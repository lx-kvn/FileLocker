# FileLocker GUI 造型探索——側欄殼子＋票根清單列定案

## 背景

這輪探索的起點是使用者想重新檢視 `7-claim-ticket.html`（v2-7「認領票根風」）這個方向的殼子
風格——側欄導覽、米白/brass 的色調。`7-claim-ticket.html` 本身在信封蠟封方向定案時就已經
被記錄為「跟信封蠟封概念相近但只做了清單頁一頁」的早期、未打磨的探索品，信封蠟封方向定案後
這條路線一度被放下，沒有繼續往下做。這輪重新把它撿回來，但範圍縮小、目標明確：

1. 只探索**整體視窗殼子**（側欄導覽＋可收合）要不要換掉現有的頂部標題列＋分頁籤排版。
2. 只探索**清單列的視覺呈現**（圖示＋撕邊的重新設計），不是重新做一次完整的加密/解密流程。

範圍刻意排除：不重新設計加密表單、密碼/Passkey 驗證彈窗、批次動畫這些信封蠟封定案文件裡
已經定案的部分——這輪動的是「外層殼子」跟「清單列本身這一個元件」，不是整個加密敘事重來。

**這輪明確要求不要延續 `7-claim-ticket.html` 本身的未打磨版型，改在 `12-file-tab-merged.html`
（已經打磨過的清單列樣式）的基礎上調整**，郵戳徽章的尺寸／文字擺放則照抄
`9-envelope-list.html` 的既有作法。所有調整都彙整進單一新檔案
`13-sidebar-ticket-shell.html`，經過十輪左右的來回調整。

實作細節（座標、CSS 技巧、踩過的坑）見〈《[側欄與票根清單_技術規格.md](側欄與票根清單_技術規格.md)》〉，這裡只記決策本身。

## 路線分工（已定案，取代先前的「尚未解決的路線衝突」章節）

上一輪留下的疑慮——票根圖示列的互動邏輯跟信封蠟封定案文件〈信封清單虛見的互動〉那節幾乎是
同一套（點擊→小幅撕開的即時回饋→驗證→驗證通過整個撕開→停留→飛走→下面補位），視覺造型卻
不同——這輪已經定案，不是二選一，是**兩套視覺分別對應不同的操作情境**：

| 情境 | 視覺方向 | 對應 mockup |
|---|---|---|
| **加密流程**（新增檔案、選擇要加密的內容、加密表單本身） | 信封蠟封 | `8-envelope-assembled.html`（折疊/寄出動畫）、`12-file-tab-merged.html`（新增檔案信封彈出表單） |
| **已加密的檔案清單**（清單列本身、解密/驗證觸發） | 票根撕邊 | `13-sidebar-ticket-shell.html` |

先前信封蠟封定案文件裡已經寫定的「加密表單信封彈出」「批次多張信封疊在一起」「寄出動畫（信封
往深處飛走）」這些跟信封形狀本身綁定的決策**維持有效，不作廢**——它們對應的是加密流程本身
（把檔案「寄」進金庫的動作），跟票根視覺負責的清單頁是兩個不同的畫面、不衝突。

**分頁合併後的正式名稱定案為「加密」**（不是先前信封蠟封定案文件暫稱的「檔案」）——`信封蠟封
方向_定案文件.md`〈加密／解密／清單合併為單一「檔案」分頁〉那節的分頁名稱要一併更新，見該
文件的對應修正。

互動邏輯（撕開/點擊→即時回饋→驗證→完整動作→飛走補位）兩套視覺共用同一套設計語言是刻意的
——使用者的操作心智模型（先摸一下、驗證、再看到完整動作）在兩個情境下應該一致，只是外殼造型
按情境切換（加密用信封，清單用票根撕邊），不是各自發明一套不同的手感。

## 側欄殼子

### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 導覽方式 | 從頂部標題列＋一排分頁籤，改成左側側欄導覽 | 使用者指定要照 `7-claim-ticket.html` 的殼子方向重新探索 |
| 側欄可不可以收合 | 可以，收合後只留圖示（不留文字），側欄本身寬度從 200px 縮到 60px | 使用者明確要求；收合鈕放在側欄最上面，跟側欄本身綁在一起，概念上乾淨 |
| 收合鈕的圖示 | 一個會依收合狀態翻轉方向的箭頭（`‹`/`›` 概念） | 用旋轉角度直接表達「這個動作是可逆的、按了會變回來」，不需要另外文字說明 |
| 收合時的文字提示 | hover 圖示才浮出文字提示（簡易 tooltip） | 收合後只剩圖示，維持基本的可辨識性；這只是先示意的簡化版本，不是最終互動細節 |
| 頂部標題列（紅綠燈＋拖曳區） | 保留在側欄殼子的最上方，橫跨整個視窗寬度，不是側欄內部的一部分 | 沿用現有 App.vue 已經驗證過的紅綠燈/拖曳區設計，這輪只換導覽方式，不重新設計視窗控制列本身 |
| 側欄分頁項目跟圖示 | 直接複製 `App.vue` 各分頁 `page-title__icon` 現有的 SVG path，不重畫新圖示 | 保留視覺一致性，也省去重新設計一套圖示語言的工作量 |
| 分頁合併後的圖示 | 加密／解密／已加密清單（依信封蠟封定案文件已經定案的分頁合併）共用一個側欄項目，圖示用「加密」分頁原本的鎖頭 | 三個裡最能代表「檔案保護」這件事本身的一個；沿用既有分頁合併決策，不是這輪新決策 |
| 資料夾防護圖示 | 沿用這輪新畫的盾牌造型（不是 `App.vue` 現有的資料夾造型圖示） | 使用者這輪明確確認「這個可以」，跟其他項目（直接複製既有 SVG）的原則不同，是唯一一個刻意換掉的圖示 |
| 密碼庫、設定圖示 | 直接複製 `App.vue` 現有的鑰匙／齒輪 SVG | 同「側欄分頁項目跟圖示」的理由 |
| 整體色調 | 沿用 `7-claim-ticket.html` 的米白/brass 色票（`--vault-steel`／`--brass` 等） | 使用者明確表示喜歡這組色調；brass 主色（`#A8770F`）剛好跟現有 `App.vue` 的 `--color-accent` 完全同一個色值，換殼子不會讓既有的強調色語意跑掉 |

## 票根清單列

### 圖層結構

一列（`.ticket-wrap`）由外而內：

- `.ticket-wrap`：負責「這一列在清單裡占多少垂直空間」，平常不設高度限制、不裁切，讓內容
  （含換行文字）自然撐開；只有真的要收合讓下面的列補位時，才由 JS 暫時鎖住高度當收合動畫
  起點（細節見下方〈技術細節〉）。
- `.ticket-stage`：負責「這一列要不要整個往旁邊飛走」的位移/淡出。
- `.ticket`：真正看得到的卡片本體（白底＋邊框＋圓角），裡面放：
  - `.ticket__seal`：一個 `<button>`，是「圖示＋撕邊」的組合，貫穿整張卡片的可視高度，
    是撕開動作唯一的觸發熱區。
  - `.info`／`.postmark-slot`／`.actions`：檔名/中繼資料、狀態郵戳徽章、操作按鈕。

### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 撕邊方向 | 垂直，不是水平 | 使用者明確要求「撕邊是要直的」，對應真正票根騎縫線的方向 |
| 撕邊要不要貫穿整張卡片 | 要，從卡片可視的上邊緣到下邊緣，只留卡片自己的內距（10px）當緩衝 | 使用者要求「橫跨整個清單列的欄位」「像真正的票根一樣」；技術上靠讓 `.ticket__seal` 用 `position:absolute` 直接掛在 `.ticket` 上（不受卡片自己 flex 排版的內距限制）達成，見下方技術細節 |
| 圖示跟撕邊的關係 | 圖示疊在撕邊正中間，像貼紙/火漆貼在騎縫線上 | 使用者明確要求；也讓「點圖示」跟「點撕邊」變成同一個熱區，不用另外處理兩種觸發來源 |
| 圖示形狀 | 圓形，帶邊線（邊線顏色跟圖示識別色一致，不是統一灰色） | 使用者詢問過意見：沒有邊線的色塊看起來像印刷上去的，不像「貼上去」的東西；加了邊線更像蠟封/貼紙，呼應這個專案本來就在用的信封蠟封語彙 |
| 圖示尺寸 | 32px（比最初嘗試的 38-40px 縮小） | 圖示太大會讓貫穿全高的撕邊看起來像兩根短短的裝飾線（使用者形容「蟑螂鬚」），縮小圖示才能讓撕邊有足夠的可見長度 |
| 點擊觸發後的完整互動時序 | ①點擊：撕開動畫的最前面一小段（極小幅度，不是另一個獨立動作）②停等 1 秒（正式版這裡是密碼／Passkey 驗證彈窗，這輪只是單純等待）③驗證通過：完整撕開，兩邊（含卡片本身的白底/邊框）真的裂成兩半，各自留有自己的撕線 ④停留一下 ⑤整列（已撕開的兩半合成一個單位）往旁邊飛走、淡出 ⑥下面的列往上補位 | 跟金庫門轉盤同一套設計語言（先給即時回饋、驗證通過才播完整動作）；「一小角」直接複用完整撕開的機制、只是縮小位移跟時長，確保跟後面接續的完整撕開是「同一個動作的延續」，不是切成兩段不相干的東西；飛走＋補位沿用信封蠟封定案文件〈信封清單虛線的互動〉已經定案的收尾邏輯 |
| 撕開範圍要不要包含卡片本身（白底/邊框） | 要，不是只有文字內容飄在卡片上面裂開 | 使用者明確要求；技術上把整張 `.ticket`（含背景/邊框）複製成兩份裁切顯示，不是只複製內部文字 |
| 撕開後兩邊要不要都看得到撕線 | 要，兩邊各自有一條完整的撕線，不是共用一條線被攔腰裁成兩截 | 原本共用一條線裁在正中央，裁完常常整條線的可見像素都分到同一邊，另一邊完全看不到；改成兩邊的撕線各自往自己那一側偏移，撕開的裁切邊界左右各留出完整一條線的空間 |
| 動作按鈕的顏色 | 全部統一成白底外框，不特別標示「主要」按鈕 | 每一列實際開放的按鈕數量不固定（1 顆或 2 顆），如果金色實心只套用在其中一顆，那顆金色按鈕在畫面上的左右位置會隨列而變、看起來像色塊亂跳；統一成同一種樣式反而比較不亂 |
| 郵戳徽章（找不到指標檔／巢狀鎖定）的樣式 | 直接照抄 `9-envelope-list.html` 的尺寸（56px 圖示＋文字並排）跟固定寬度欄位做法 | 使用者明確要求；郵戳圖示本身沿用既有素材 `Postmark_Warning.svg`／`Postmark_Nested_Lock.svg`，不重畫 |
| 郵戳徽章的水平位置 | 固定，不隨旁邊按鈕數量變動 | 使用者明確要求；技術上給動作按鈕欄位固定寬度（180px）＋靠右對齊，不管按鈕數量多寡，郵戳欄位前面的空間都一致，這點也是照抄 `9-envelope-list.html` 已經處理過的同一個問題 |

## 技術細節（實作時可以直接沿用的做法，不用重新推導）

- **撕開效果的實作方式**：`.ticket__seal` 觸發時，JS 把當下這一列唯一互動層 `.ticket` 整份
  `cloneNode(true)` 兩份，分別加上 `.ticket__half--left`／`--right`，用 `clip-path: inset()`
  各自只露出撕線左右兩側（裁切點用 JS 即時量測 `.ticket__seal` 的實際中心點 `offsetLeft +
  offsetWidth/2`，不是猜一個寫死的 px 值）。平常兩份疊在原本的 `.ticket` 上面、opacity:0，
  看起來就跟只有一份一樣；撕開時原本的 `.ticket` 淡出、兩個半邊淡入並往外 `translateX`+
  `rotate`，看起來像真的裂開。
- **撕邊要貫穿整張卡片、不受卡片自己 padding 限制**：關鍵是讓 `.ticket__seal`（連同裡面的
  撕線）用 `position:absolute` 直接掛在 `.ticket`（`position:relative`）上，`top:0;bottom:0`——
  absolute 子元素的 top/bottom 是相對容器的 padding box 量，不會被 `.ticket` 自己的 flex
  排版跟內距影響。踩過的坑：一開始撕線容器（`.ticket__seal`）還是普通 flex 子元素、靠
  `align-self:stretch` 撐高，撐出來的高度只跟旁邊文字內容一樣高（雙行文字約 39px），圖示
  本身 32px 置中疊上去之後幾乎整個容器都被圖示的白底圓圈蓋住，撕線技術上「有畫」但完全看
  不見——不是顏色對比度問題（一開始誤判成對比度問題，調過顏色沒解決，後來才找到真正原因）。
- **兩邊撕線各自完整可見**：`.ticket__half--left .ticket__tear-line{left:calc(50% - 2px)}`／
  `.ticket__half--right .ticket__tear-line{left:calc(50% + 2px)}`，讓兩邊的撕線各自落在自己
  那一側裁切邊界內側 2px，撕開時才不會被 `clip-path` 邊界正好切成兩段各自只剩一半可見。
- **收合／飛走動畫不能同時做**：整列收合（`max-height` 轉場）跟飛走位移（`translateX`）如果
  同時疊加，`overflow:hidden`（收合必須要有，否則沒辦法把高度平滑收到 0）會把還在飛的內容
  攔腰裁掉，看起來像卡到外面去。解法是嚴格分兩個階段接續播放，不重疊：先播完飛走＋淡出（此時
  `.ticket-wrap` 完全不設 `overflow`/`max-height`，畫面上想飛多遠都不會被裁），確認飛走動畫
  真的播完（畫面上已經看不到任何東西）之後，才用 JS 量測當下 `scrollHeight` 當起點，開始收合
  高度動畫。
- **郵戳徽章固定寬度欄位**：`.postmark-slot{width:90px}` 是獨立欄位，`.actions{width:180px;
  justify-content:flex-end}` 讓按鈕數量變化只影響按鈕在欄位內部靠右的起始位置，不影響欄位
  本身的寬度——這樣郵戳欄位前面可用的空間才會固定，不會因為隔壁 `.info`（`flex:1`）欄位
  吸收/釋放空間而跟著飄移。

## 已知限制

- `.ticket__half`（撕開時顯示的兩個半邊）是整份 `.ticket` 的 DOM clone，每一列在頁面載入時
  就會多出兩份幾乎一樣的 DOM——這輪清單只有 6 列，效能上沒有感覺，但如果之後清單筆數很多
  （例如上百筆），這個「每列預先複製兩份」的做法要重新評估，可能要改成撕開當下才動態建立
  clone、播完就移除，不要整份清單一次全部預先複製。
- 撕線在批次加密（`--brass-tint` 底色）那一列用了不同的顏色覆蓋（`var(--brass-deep)`），
  其餘列統一用 `var(--ink-faint)`——這是手動個別覆蓋，不是自動依底色算對比度，如果之後又有
  新的底色變化（例如深色模式），需要重新手動確認每一種底色情境下撕線的對比度還夠不夠。
- 收合側欄的 hover 提示（tooltip）只是先示意的簡化版本，沒有處理視窗邊緣被截斷、鍵盤 focus
  時要不要也顯示提示等細節。

## 待辦事項

- **視窗控制鈕風格切換**：新增一個設定，讓關閉／最小化／最大化按鈕可以在 macOS 造型（圓點、
  左上角、關閉/最小化/最大化順序）跟 Windows 造型（方形圖示按鈕、右上角、通常是最小化/
  最大化/關閉順序）之間切換。兩種風格都還是用 Vue 做（`.traffic-light` 這組元件本身），不是
  換成原生系統控制項，只是位置跟造型換一套。這輪 mockup 固定用 macOS 造型，沒有做切換功能，
  `13-sidebar-ticket-shell.html` 裡也用程式碼註解記錄了同樣的內容。
- **檔案類型辨識邏輯**：這輪每一列的圖示、識別色都是寫死在 mockup 裡的範例資料，正式串接時
  要依實際檔案（副檔名／MIME type／是不是資料夾）判斷出檔案類型。
- **圖示比對邏輯**：判斷出類型之後，要有一份「類型 → 圖示／識別色」的對照表，不是每個類型
  各自散落寫在畫面裡；也要決定「無法辨識/不支援的類型」要顯示哪一種預設圖示——這輪 mockup
  沒有這個 fallback。
- 收合側欄的收合斷點（視窗多窄以下要不要自動收合）、hover 提示的完整互動細節，這輪都沒有
  問過，只做了「按鈕手動觸發收合」這一種操作方式。
