## 1. 信封蠟封方向

### 1.1 背景

這個方向的起點是使用者手繪的設計稿 `設計策略_v1.jpg`：把「加密」比喻成「把檔案裝進信封、蓋上蠟封寄出」，涵蓋三個階段——填寫加密表單（信封打開，露出輸入框）、剛完成加密（信封闔上、蓋章）、在清單中跟其他項目一起顯示（信封壓扁成一列）。這是本輪造型探索裡第一個把「造型比喻」延伸到整個加密流程、而不是只套用在單一畫面的方向，之前的「認領票根」（`7-claim-ticket.html`）概念相近但只做了清單頁一頁。

這份文件記錄延伸這個方向前，跟使用者一題一題確認過的細節，供之後正式製作 mockup／移植回 `App.vue` 時對照，不要憑印象重新猜一次。

### 1.2 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 信封比喻的套用範圍 | 只用在**加密流程、已加密清單、解密流程**這三個地方 | 這幾頁的核心動作都是「把檔案裝進去/從裡面取出來」，信封「裝東西寄出」的敘事直接對應。資料夾防護、密碼庫、設定這幾頁的動作性質不同，硬套信封比喻反而牽強 |
| 資料夾防護頁的視覺語言 | 不套信封，改用**保險箱／金庫門**（closed／open 兩態） | 使用者明確指出：資料夾防護是「整個空間被限制存取」，不是「內容被移走封起來」，跟信封寄送的敘事本質不同；金庫門可以延用信封蠟封那組金色/紅色當呼應色，但形狀完全獨立，不是信封的變形 |
| 密碼庫、設定頁 | 這輪未定案，不套信封，維持既有／其他版本的處理方式 | 使用者只點名了加密/清單/解密/資料夾防護四頁，其餘沒有要求延伸，不擅自擴大範圍。**後續進度**：密碼庫已在第 4 節〈密碼庫筆記本方向〉獨立定案（筆記本語彙），設定頁本身目前仍維持中性風格未套用任何主題 |
| 加密表單那個尖角信封封口，窄視窗下怎麼辦 | **尖角高度跟著寬度縮短，維持比例**，不會在某個寬度直接砍掉變成一般矩形表單 | 使用者要求視覺上「始終是一個信封」，不接受降級成標準表單卡片這種安全但沒有個性的處理方式 |
| 批次加密（一次選多檔案）怎麼表現 | **一疊信封疊在一起**（像現實中好幾封信一起寄出的樣子） | 直接、直覺地表達「這是好幾份東西」的數量感，跟單一檔案的單一信封形成自然的數量對比，不需要額外的數字徽章說明 |
| 深色模式下，牛皮紙＋紅蠟這套配色怎麼處理 | **牛皮紙換成深褐色／皮革色，紅蠟保留原色** | 紅蠟在深色背景下依然要醒目（这是視覺焦點，不能跟著整體變暗變得不明顯）；牛皮紙換成深皮革色是為了維持「信封是個實體物件」的材質感，不是簡單把亮度調低這種偷懶做法（那樣會讓信封看起來像髒污的紙，跟其他深色元素的對比也不夠） |
| 既有清單元素（巢狀鎖定 ×N 徽章、「找不到指標檔」警告、分類分組）怎麼套進信封列 | 通通**當成信封上的郵戳／標籤，貼在信封角落** | 延續「這是一封實體信」的敘事——真正寄送過的信件本來就會貼各種郵戳跟標籤，讓這些狀態徽章有理由用插畫感的郵戳造型呈現，而不是通用的圓角文字徽章 |
| 清單列裡的虛線（檔名與蠟封之間）的意義 | **可點擊，是解密的替代觸發入口**，完整互動流程見〈1.6 信封清單虛線的互動〉 | 這輪定案，取代原本「純裝飾、保留位置」的暫定狀態 |

### 1.3 需要使用者手繪、素材庫目前沒有的圖示

已存在、可直接沿用的（`src/FileLocker.Web/src/assets/`）：`Locked_Wax_Seal.svg`、`Passkey_Black/White.svg`、`Recovery_Key_Black/White.svg`、`Lock_Dark/Light.svg`。

這輪定案後、素材庫裡還沒有、建議比照 `Locked_Wax_Seal.svg` 的畫風補畫的。「打開的信封＋頂端蠟滴」因為要做封口折疊動畫，不能畫成一張攤平的圖，必須拆成可以個別旋轉、個別控制正反面的獨立圖層（細節見下方〈1.4 折疊動畫的圖層結構〉）。

### 1.4 折疊動畫的圖層結構

按下加密後，封口三角形要能單獨往下折、蠟滴要能在折疊過程中自動從「反面（只有反光）」翻成「正面（完整細節）」——這需要 CSS 的雙面翻轉技巧（`backface-visibility`），素材要照這個結構拆檔，不能是一張完整的信封插圖：

- `Envelope_Flap.svg` 是會旋轉的封口紙本體，`Wax_Drip_Back.svg` 疊在它上面同一個位置，維持跟封口一樣的旋轉角度（封口打開時先露臉，只有反光沒有圖案）。封口完全折下去、翻到正對鏡頭那一刻，瀏覽器自動改顯示的「正面」**不是另外一張圖**，直接引用 `Envelope_Wax_Seal.svg`（預先轉 180 度，跟 `Wax_Drip_Back` 疊在同一個位置）——正反兩面翻過去露出來的圖案，內容跟「完成畫面／清單列」共用的蠟封徽章本來就該是同一個東西，沒必要重畫一份 `Wax_Drip_Front.svg`（原本文件裡有這條，後來發現是多餘的，拿掉了）。

> **實作補充（技術規格已驗證，跟這段文字描述有落差，實作時以技術規格為準）**：實際 mockup 驗證下來，蠟封的正反面切換並不是靠 `backface-visibility` 貼圖切換，而是「蠟封獨立於封口紙旋轉之外、疊在同一個父層座標系裡的子元素，闔上時用 `rotateX(180deg)` 抵銷父層翻轉」的做法，細節見《[GUI造型探索_技術規格.md](GUI造型探索_技術規格.md)》第 1 節。這是使用者用「現實中蠟封不會跟著信紙一起翻面」的實體邏輯推翻舊方案後定案的，記錄在這裡避免以後照這段文字重新畫素材或重寫 CSS。

### 1.5 資料夾防護頁（金庫門）

資料夾防護分頁的金庫門造型、圖層結構、清單列互動細節，以及「新增資料夾」的完整開門儀式，已獨立成本文件〈[2. 資料夾防護（金庫門）](#2-資料夾防護金庫門)〉一節。金庫門跟信封是服務不同分頁、不同操作性質的兩套造型語言，獨立成一節方便查找，不代表兩者互不相關。

### 1.6 加密／解密／清單合併為單一「加密」分頁

> **分頁名稱更新**（見〈[3. 側欄與票根清單](#3-側欄與票根清單)〉〈路線分工〉）：下方原訂的暫稱「檔案」已改為正式定案「加密」，本節其餘內容（合併範圍、入口、決策記錄）不受影響，僅名稱更新。合併後分頁的清單畫面視覺改用票根撕邊造型（見第 3 節），加密流程本身（新增檔案、選檔案、設密碼）維持信封蠟封造型，兩者是同一個分頁內的兩種畫面，不是互斥的兩套方向。

現況（探索階段已查證 `App.vue`，非猜測）：`activeTab` 目前有 6 個分頁——`encrypt`／`decrypt`／`list`／`folderGuard`／`passwordLocker`／`settings`。其中 `encrypt` 已經是兩步驟精靈（步驟一：選檔案，畫面是 dropzone＋已選檔案列表，可個別移除，「下一步」按鈕在沒選檔案時 disabled；步驟二：密碼／Passkey／恢復金鑰設定），`decrypt` 是單一表單（路徑輸入框＋選檔按鈕＋密碼欄，一次只處理一個檔案，沒有批次），`list` 是已加密項目清單，每一列有自己的解密操作（含〈1.7 信封清單虛線的互動〉那套虛線觸發）。

這輪定案：把 `encrypt`／`decrypt`／`list` 三個分頁合併成一個分頁（暫稱「檔案」，現已定案為「加密」），分頁欄從 6 個減到 4 個（加密／資料夾防護／密碼庫／設定）。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 合併後分頁的預設畫面 | **清單**（原本 `list` 分頁的內容），不是加密表單 | 跟資料夾防護分頁的既有結構一致——資料夾防護分頁本來就是「清單為主體＋新增資料夾按鈕觸發新動作」，這次合併是讓「加密」分頁跟它同一套結構，不是另外發明一種 |
| 進入加密流程的入口 | 清單畫面上方的**「新增檔案」按鈕**，按下後信封彈出（跳進來→打開），接著是選檔案／設密碼兩步驟 | 對應使用者原話「按下加密後跳出信封，然後多一個頁面，選檔案的頁面」——選檔案這一步沿用 `encrypt` 步驟一既有的邏輯（dropzone＋已選清單＋移除），只是包進信封的視覺容器裡，不是重新設計一套新的選檔案互動 |
| 「選擇要解密的檔案」按鈕的適用範圍 | **只服務不在清單裡的外部 `.locked` 檔案**（例如別人給的、從備份還原回來的），不是拿來取代清單列本身的解密操作 | 清單裡的項目已經有自己的解密入口（虛線觸發，見〈1.7 信封清單虛線的互動〉），「我知道要解哪個、它就在清單裡」跟「我手上有一個不在清單裡的檔案、要指定路徑去解」是兩種不同情境，合併分頁不能讓後者的存在抹掉前者，兩個入口保留、各自服務各自的情境 |
| 加密步驟一（選檔案）要不要重新設計 | **不用**，沿用 `encrypt` 分頁步驟一現有的邏輯（dropzone、已選檔案列表可個別移除、「下一步」在未選檔案時 disabled） | 使用者描述的「選完後在裡面顯示有哪些檔案的名稱，然後下面有取消跟下一步的按鈕」跟現有實作幾乎一致，這次改動的是「包進信封視覺容器」跟「分頁結構」，不是選檔案這一步的互動邏輯本身 |
| 步驟一原本的「下一步」按鈕，合併後是不是要改叫「取消」/「下一步」 | 沿用兩顆按鈕的語意（返回上一步／繼續），使用者原話用了「取消」這個詞，但實際指的應該是「放棄這次新增、關掉信封退回清單」，不是清空已選檔案 | 「取消」在既有 `encrypt` 步驟一沒有對應按鈕（現有只有「下一步」，沒有「上一步」因為就是第一步），合併進信封情境後多了「關掉信封退回清單」這個新狀態，需要額外定案。**確切行為仍未定案**，見〈7.1 待辦事項——信封蠟封方向〉 |

#### 選檔案步驟的信封排版

「新增檔案」信封彈出後，裡面的選檔案／已選清單這步（`12-file-tab-merged.html` mockup）延伸出幾個新定案：

| 決策點 | 結論 | 理由 |
|---|---|---|
| 「拖曳檔案，或」＋「選擇檔案」按鈕放在信封的哪個位置 | 放進 `Envelope_Body.svg` 本體圖檔裡**烤進去的裝飾三角形**（信件圖示＋線條那塊，量測落在畫布 32.07%~54.54% 之間），不是封口那個摺邊三角形 | 這塊裝飾三角形原本只是靜態裝飾，重用它當互動內容的容器，不用另外找地方放；封口三角形是折疊動畫用的可動零件，語意上不適合放靜態的操作內容 |
| 「新增檔案」標題文字 | **拿掉**，不放在信封裡任何位置 | 跟外面工具列上觸發這個彈窗的「新增檔案」按鈕文字重複，信封打開後不需要再講一次同樣的話 |
| 信封本體圖示要不要分狀態 | **要，分四級（0／1／2／3 以上），不是原本設想的「空/有東西」二選一**：`Envelope_Body_Empty.svg`（0）／`Envelope_Body_One.svg`（1）／`Envelope_Body_Two.svg`（2）／`Envelope_Body.svg`（3 以上封頂，重用現有素材不用重畫） | 用信封「裡面裝了幾樣東西」直接對應「選了幾個檔案」這個資料狀態，比單純「有沒有」更貼合信封比喻，也給使用者一個不用數清單就能感覺到數量的視覺回饋；封頂在 3 是刻意的收斂，不然要一路畫到「裝 87 個東西的信封」沒有意義 |
| 拖曳檔案懸停在信封上時的回饋 | 三件事一起發生：①本體圖示切成對應張數的版本（見上一列，預覽放開後的樣子）②「拖曳檔案，或」提示字隱藏（懸停中這句話是多餘的）③信封外圍加一圈偏下方的陰影（`filter:drop-shadow()`，只給 Y 軸正值位移，不給 X） | 三個回饋分別對應「這裡是有效目標」「不需要再提示怎麼做」「視覺上浮起來、準備接收」，合起來給懸停中的使用者足夠的確認感；沒放開前就先讓使用者看到「放開後會怎樣」是刻意的誠實預覽，不是等放開才顯示結果 |
| 懸停階段能不能準確預覽張數（不是統一先顯示 1 張再等放開修正） | **可以，下一輪實作時要做進去**：瀏覽器拖放 API 的 `event.dataTransfer.items`（不是 `.files`，`.files` 只有在 `drop` 那一刻才有內容）在 `dragenter`/`dragover` 階段就能拿到正確的拖曳項目數，用 `item.kind === 'file'` 篩掉非檔案項目後，`items.length` 在懸停中就是準的，不用等放開才知道實際張數 | 這個 mockup（`12-file-tab-merged.html`）用滑鼠 hover 模擬懸停，沒辦法模擬「拖了幾個檔案」這件事，所以先用保守版本（固定顯示 1 張）頂著；真正串接 `dragenter`/`dragover` 時要接上 `dataTransfer.items`，讓懸停預覽直接顯示正確張數，不是這個 mock 目前簡化過的行為 |
| 已選檔案清單的高度 | **固定高度**（不隨筆數增減），清單本身用獨立的邊框跟外面的操作區（繼續新增連結、取消/下一步按鈕）隔開 | 清單筆數變動時，如果高度跟著長縮，下面的按鈕會跟著上下移動，使用者「繼續新增」時畫面一直跳動；固定高度＋內部捲動，只有清單自己在動，其餘元素（含信封本身）位置不受影響 |
| 「新增檔案」信封整層彈窗的垂直對齊方式 | **固定頂部對齊**（不是整層置中） | 清單長高時如果整層彈窗用置中對齊，flex 置中會重新計算，連信封本體都會跟著往上跳；固定頂部對齊之後，信封的位置就跟底下清單的高度脫鉤，不會因為清單長度不同而整組漂移 |

實作細節（座標、CSS 技巧、踩過的坑）見《[GUI造型探索_技術規格.md](GUI造型探索_技術規格.md)》對應章節，這裡只記決策本身。

### 1.7 信封清單虛線的互動

跟金庫門轉盤同一套設計語言——**先給即時觸碰回饋，驗證通過才播完整動作**：

1. 點擊虛線 → 虛線先撕開一小段（即時回饋，呼應「摸到了」的感覺）
2. 跳出驗證流程（跟解密共用同一套密碼／Passkey 驗證）
3. 驗證成功後，整個「籤頭」被撕開——原本欄位內容重組成「籤頭」＋「欄目原本的東西」
4. 停留約 0.5 秒
5. 整列（籤頭連同其餘部分）往旁邊飛走，下面的列往上補齊空出來的位置

跟轉盤的規則一致：不論從虛線或從「解密」按鈕觸發，驗證成功後撕開飛走的完整動畫都會播放；撕開的前導動作只在直接點虛線時才有。

> **後續發展**：這套互動邏輯在〈[3. 側欄與票根清單](#3-側欄與票根清單)〉那輪被沿用到票根撕邊清單列（視覺造型換成票根，互動邏輯不變）。

### 1.8 「寄出」動畫與加密交易模型（第四階段）

在既有的折疊動畫（開⇄闔）之後，追加第三個動畫段落：信封闔上、顯示檔名＋郵戳之後，**整個信封往前傾斜、往畫面深處飛走**，模擬「信被寄出去」。這一輪確認下來，這個動畫牽動的不只是前端 CSS，還改動了 `LockService.EncryptAsync`（`src/FileLocker.Core/LockService.cs`）目前的交易模型——現況是「加密寫入 Vault → metadata → 指標檔 → 刪除原始檔」這一串依序、不可分割地一次做完，中間沒有任何使用者確認點（探索階段已確認，非猜測）。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 動畫觸發時機 | **不自動接續**，信封闔上顯示檔名+郵戳後停下來，等使用者按「確認」或「取消」 | 讓使用者有真正的反悔機會，不是純裝飾性的停頓 |
| 「取消」的語意 | **取消＝回滾加密本身**，不是只取消動畫 | 使用者要的是「按取消＝這個檔案沒有真的被加密過」這種完整的可逆性 |
| 加密的執行時間點 | 按下密碼確認、折疊動畫開始播放的同時，**就開始真正加密**（寫入 Vault + metadata），但**先不放指標檔、不刪原始檔** | 這樣「取消」才有東西可以回滾（只要刪掉 Vault 裡這筆暫存項目），且不動原始檔案，回滾永遠是安全的 |
| 暫存狀態怎麼標記 | metadata（`.meta.json`）新增狀態欄位 **`pending` / `committed`** | 沿用既有的 metadata 檔案，最小改動；不另外新增暫存標記檔格式，避免多一套「轉正」邏輯要處理 |
| 中途關閉 App（pending 期間當機/關閉）怎麼處理 | 下次啟動掃到 `pending` 狀態的項目，**安全自動回滾**（刪除該筆 Vault 暫存項目） | 因為 `pending` 狀態保證原始檔案還在、使用者從頭到尾沒按過確認，回滾不會遺失任何東西。**明確不能**用「指標檔不存在」去推斷孤兒項目要不要清掉——那可能是別的原因（例如指標檔被使用者手動刪除），跟這裡的「未 finalize」是兩種不同情境，不能用同一套判斷邏輯，否則可能誤刪合法但指標檔遺失的加密紀錄 |
| 按下最終確認後 | **先讓 finalize（刪除原始檔＋放指標檔）真的完成，動畫才開始播**，等待期間信封上疊加「處理中...」文字 | 飛走動畫語意上等於「這份檔案真的處理完成了」，如果背地裡還沒做完就先演給使用者看，一旦 finalize 失敗（例如原始檔刪除失敗）會出現「畫面說完成但實際沒完成」的信任問題，尤其是加密敏感檔案的操作，正確性優先於流暢度 |
| 按下取消 | 刪除剛才寫入 Vault 的 `pending` 項目，**原始檔案全程沒被動過**；信封重新打開，退回加密表單畫面 | 跟現有「重新打開」互動一致，不需要另外設計新的中間態畫面 |
| 批次加密（一次選多檔案） | **整批視為一個交易**——全部加密完才一起顯示、一起確認/取消，沒有逐檔案分開決定的 UI | 使用者一次選取多檔、一次按下加密，心智模型是「這是一個動作」，確認流程不該比操作本身更細緻 |
| 飛走的方向 | **固定裝飾性方向**：整個信封（連同疊在上面的檔名＋郵戳）往前傾斜，往畫面深處飛走（用縮小＋位移模擬飛遠，不是滑出螢幕邊緣），過程中漸層模糊（`filter:blur()`）＋淡出 | 瞄準「已加密清單」分頁的實際座標在動態排版下技術上複雜（側邊欄收合、視窗大小都會影響），投入產出比不划算；固定方向已經足夠傳達「完成、離開這裡」的意涵 |
| 動畫播完之後 | **自動切換到「已加密清單」分頁**；清單先正常顯示既有項目，接著剛完成的這筆**從旁邊滑入，把原本的項目往下推**，最終停在清單最上方 | 敘事上「這份東西離開這裡、去了該去的地方」，如果切分頁後不做任何進場動畫，敘事斷在半路 |
| 是否可重播 | **只播一次，不提供重播** | 這是「一次性事件」動畫（同一類：刪除、新增），不是常態互動，清單裡的項目已經有自己的呈現方式，過度使用會讓這個特效失去「一次性儀式感」的意義 |
| 信封怎麼出現（開場） | **從畫面正上方垂直落下**（正交、不帶透視/傾斜角度），落到定點時輕微超過再回彈，回彈的力道**順勢帶開封口、直接接續打開信封**——不需要額外的觸發點，是同一段連續動作 | 首尾呼應：結尾是「傾倒→飛走」，開頭對應是「落下→回彈→打開」，兩段都是一鏡到底、不需要使用者額外操作的連續動態 |
| 信封出現的起始位置／來源 | **固定從畫面正上方彈出，不追蹤使用者選取檔案的來源座標** | 觸發加密的來源可能是右鍵選單、拖曳、清單按鈕，甚至來自檔案總管視窗，動態算出合理起始座標的技術成本遠高於固定方向的效果增益 |
| 表單填完按確認之後 | **表單內容原地換成加密進度條**（信封維持打開狀態，不是先闔上才顯示進度），進度條反映**真實加密進度**（依實際寫入 Vault 的位元組數計算百分比，不是裝飾性的固定時長動畫） | 真實進度條在小檔案（幾乎瞬間完成）跟大檔案/資料夾（需要讓使用者知道還要等多久）兩種情境下都比裝飾性動畫誠實；這代表 `LockService.EncryptAsync` 需要新增進度回報機制，目前完全沒有 |
| 闔上後的郵戳徽章內容 | 郵戳**下方**要顯示加密時間（時間戳記），不是只有郵戳圖案本身 | 對應設計稿「剛完成加密檔案的階段」那張手繪稿裡，檔名下方本來就有日期/大小/編號的小標籤，這次明確定案「加密時間」要出現在郵戳下方 |
| 按取消之後表單狀態 | 信封重新打開時，**密碼欄位跟 Passkey／恢復金鑰的勾選狀態都要保留**，不清空 | 使用者只是想再想一下或取消寄出這個動作，不代表想放棄已經填好的設定，清空等於強迫重新輸入一次密碼，是明顯的體驗浪費 |

### 1.11 獨立解密流程（信封＋Sheet）

#### 背景

合併分頁（〈1.6〉）保留了「選擇要解密的檔案」這個入口（`decrypt.pickLockedFile`），服務不在清單裡的外部 `.locked` 檔案，但這個表單本身要不要套用信封造型，先前一直沒有定案過——這輪 grilling 補上這塊空白，順帶重新設計了整段互動，不只是「要不要套殼」的問題。

現況查證（`App.vue`，非猜測）：

- 現有「解密」表單是獨立分頁，欄位為路徑輸入框＋「選擇 .locked 檔案」按鈕＋密碼欄＋解密按鈕，若該檔案有開 Passkey／恢復金鑰會多顯示對應的替代按鈕。
- 清單解密（Files 分頁裡的「解密」／Passkey／恢復金鑰按鈕）目前三種驗證方式都會先跳 `askChoice` 彈窗問「還原到原始位置」還是「自選位置」（`decryptFromList`／`decryptFromListViaPasskey`／`decryptFromListViaRecoveryKey`，3152／3279／3303 行一帶），選「自選位置」才會呼叫 `sendMessage('pickFolder', { purpose: 'decryptDestination' })`。
- History 分頁（`list.subTabHistory`）目前是純資訊表格（檔名／動作／時間／明細 4 欄），完全沒有任何操作按鈕。
- 「開啟檔案位置」不需要新增後端功能——`MainWindow.xaml.cs` 的 `HandleOpenFolderInExplorer`（呼叫 `explorer.exe /select,`）已經是既有機制，直接重用。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 觸發方式 | 按下「選擇要解密的檔案」**直接跳原生選檔視窗**，不先跳信封 | 信封是「確認這是一個合法加密檔案」之後才要演的儀式，選檔前信封無事可做 |
| 選檔完成後的合法性檢查 | 前端先送新的 `readLockedFileMetadata` 訊息（只讀檔頭中繼資料：檔名、加密時間、是否啟用 Passkey／恢復金鑰，**不需要密碼**），讀取失敗直接用既有 toast 錯誤機制顯示「不是有效的加密檔案」，**不播信封動畫** | 只在確認是合法檔案後才讓信封出現，避免對一個打不開的檔案演一整套儀式感動畫；這代表 `LockService`／對應 Core 服務要新增一個唯讀 metadata 的介面，目前沒有 |
| 信封出現的動畫 | 沿用〈1.8〉「從正上方垂直落下＋回彈」的既有開場，但**回彈後停在關閉態**（不順勢打開封口），信封上標示檔名＋加密時間（比照 `8-envelope-assembled.html` 完成態的郵戳呈現） | 同一個 App 內「信封怎麼出現」保持同一套語言，差異只在落地後的下一步不同，不需要為這個情境另外設計一套進場動畫 |
| 停等時間 | 信封落地後停 **0.5 秒**才抽出 sheet | 給使用者時間看清楚信封上的檔名／時間，跟後面「驗證成功打勾」的停等時長（見下方）取同一個數字，維持整段動畫節奏一致 |
| sheet 的抽出方式 | 沿用〈5.2〉已定案的兩段式滑動（先完全抽出露出全貌，再收回疊上信封範圍） | 跟已選檔案清單卡片、恢復金鑰畫面共用同一套容器語言，不用重新設計 |
| sheet 初始內容 | 密碼輸入框＋送出按鈕（按 Enter 也觸發同一動作）；若該檔案有開 Passkey／恢復金鑰，額外顯示對應按鈕。Passkey／恢復金鑰按鈕圖示重用既有 `Passkey_Black/White.svg`／`Recovery_Key_Black/White.svg` | 沿用既有解密表單的驗證方式組合，只是容器換成 sheet；圖示不重畫，跟其他驗證彈窗一致 |
| 「使用恢復金鑰」的頁面切換 | sheet 內部用 `translateX`／`clip-path` **左右滑動**切到恢復金鑰輸入畫面，該畫面有「返回」可以滑回原本內容 | 這是同一張紙卡「翻頁」，不是抽出新的一張，滑動比淡出淡入更貼近「翻到另一面內容」的直覺，不需要引入新的動畫手法 |
| Passkey 自動觸發 | 若原加密時有開 Passkey，sheet 一出現就**自動**跳 Windows Hello 驗證視窗，不用使用者手動點按鈕 | 呼應金庫轉盤「先給即時回饋」的既有節奏——Passkey 是最快的路徑，能自動就不要求多一次點擊 |
| Passkey 驗證失敗／使用者取消 | **退回顯示 sheet 正常內容**（密碼欄＋Passkey／恢復金鑰按鈕都還在），不自動重試、不跳錯誤彈窗，只在 sheet 上用小段文字提示「Passkey 驗證未完成，可以重試或改用密碼」 | Windows Hello 取消是常見操作（手滑、想不起哪根手指），不該用強制性錯誤彈窗打斷；使用者可以自己選重試或改用其他方式 |
| 驗證成功回饋 | sheet 上打勾顯示「驗證成功」，停留 **0.5 秒**才開始反向動畫 | 跟信封落地後的停等數字一致，統一節奏；也讓使用者有基本時間看清楚回饋 |
| 驗證成功後的收尾動畫 | sheet 抽出動畫**倒放**（紙條塞回信封後面）→ 信封打開 → **自動**抽出新的 sheet 顯示「選擇存檔位置」按鈕 | 呼應〈1.8〉「金鑰紙卡緊接著冒出來」的既有敘事節奏，同一套容器語言重複使用，不用另外設計新的收尾方式 |
| 存檔位置 sheet 按取消 | **收回 sheet，退回「信封開著、空的」狀態**，不整個關閉、不做任何檔案還原（到這步為止只是驗證了權限，實際寫入要等使用者真的選定存檔位置） | 呼應〈1.8〉「先讓 finalize 真的完成，動畫才開始播」的既有原則——按取消時還沒寫過任何東西到目的地，不需要額外回滾邏輯 |
| 「信封開著、空的」狀態要不要有出口 | **要兩個**：一顆「選擇存檔位置」按鈕（重新喚出存檔 sheet），加一個文字連結「取消」（整個關閉退回清單，不寫入任何檔案） | 使用者按取消可能是「選錯資料夾想重選」或「整個不想解密了」兩種心思，只留其中一種會逼使用者用不對的方式達到目的 |
| 清單解密（Files 分頁既有互動）要不要也套這套信封＋sheet | **不要，維持既有撕票根互動**，只拿掉「詢問存到哪裡」這一步，改成**直接還原到原始位置** | 〈第 5 節〉範圍已明確排除清單列本身的撕開互動；清單解密走的是跟金庫轉盤共用的既有語言，服務「我知道要解哪個、它就在清單裡」這種情境，跟這次服務「手上有一個不在清單裡的外部檔案」的信封流程是不同操作起點，沒必要共用視覺 |
| History 清單新增「開啟檔案位置」按鈕的適用範圍 | **解密跟上鎖（加密）兩種動作類型的紀錄列都要**——解密指向還原後的位置，加密（上鎖）指向留在原位置的 `.locked` 指標檔位置；其餘動作類型（不涉及檔案位置概念）不顯示這顆按鈕 | 加密動作本身也會在原位置留下 `.locked` 指標檔，同樣有「打開來看看在哪」的需求，不是只有解密才需要 |
| 獨立信封解密流程的結果要不要寫進 History | **要，跟清單解密共用同一份歷史紀錄**，不另開一份 | 兩種解密方式的紀錄要能在同一個地方查得到，「開啟檔案位置」按鈕才對兩種來源都有效 |

## 2. 資料夾防護（金庫門）

### 2.1 背景

金庫門（保險箱／轉輪＋門扇）的造型比喻最早是在〈第 1 節 信封蠟封方向〉裡，跟信封那套一起定案的——當時只確認了圖層結構跟清單列常態的互動細節，「完整開門動畫（框架＋門扇＋轉輪整套）究竟在使用者操作的哪個時間點出現」這件事其實從未真正定案過，只寫了轉輪單獨旋轉的部分，沒有指定門扇何時打開。

這份文件把資料夾防護專屬的金庫門決策獨立成一節，原因有二：一是金庫門跟信封是兩套完全獨立的造型語言（服務不同分頁、不同操作性質），混在同一節裡之後回頭找資料夾防護的細節要大海撈針；二是這輪 grilling 補上的「新增資料夾的開門儀式」是一段先前完全沒有處理過的新流程，適合獨立記錄，不是舊決策的修訂。

原本第 1 節裡的〈金庫門動畫的圖層結構〉〈金庫門分頁的互動細節〉兩節（含決策記錄表）已整段移入本節。

### 2.2 金庫門動畫的圖層結構

資料夾防護頁的金庫門，最後決定不走跟信封同等複雜度的「轉盤／把手／門閂各自獨立」四拍模擬，改成參考常見的金庫圖示慣例——用**一個帶輻條的大轉輪同時代表轉盤跟把手**（不分開畫兩個零件），門閂也不特寫，只靠門體本身的開合傳達「鎖住/打開」。動畫收斂成兩拍：

1. **轉輪旋轉**（`rotateZ`，原地自轉，代表輸入密碼＋扳動開鎖一次做完）
2. **門扇打開**（`rotateY`，繞鉸鏈轉開，角度封頂在 70-80 度、不轉到會露出門背面的角度，`ease-in-out`，450-550ms，門扇是最後一步、份量最重）

三層各自的職責：

- `Vault_Frame.svg`（已定案）：固定不動，外殼＋凹陷開口＋鉸鏈缺口＋開口邊緣內陰影
- `Vault_Door_Slab.svg`：門體本身，不含轉輪，鉸鏈那一側要畫出鉸鏈細節對上 `Vault_Frame` 的缺口位置，尺寸要能剛好蓋住開口
- `Vault_Wheel.svg`：轉輪本身，疊在門體正中央，黃銅金色、細線條風格跟其他素材一致，自己原地旋轉

> **鉸鏈位置（技術規格已驗證，實作時直接沿用）**：這節文字最早寫「鉸鏈定案在右側」，但實際 mockup（`10-vault-door.html`）驗證下來，門扇鉸鏈是**左側**（`transform-origin:21%`）——這是舊文件本身遺留、從未回頭修正的落差，現在一併訂正。以《[GUI造型探索_技術規格.md](GUI造型探索_技術規格.md)》第 3 節（含 `Vault_Frame.svg`／`Vault_Door_Slab.svg` 實際的鉸鏈缺口位置）為準。轉輪與門扇的精確 CSS keyframe、時序常數（`WHEEL_OPEN_MS=650`、`WHEEL_CLOSE_MS=780`、`DOOR_MS=500`、接力時序、「喀」一聲回彈手感）都記在同一份技術規格文件第 3 節，這裡不重複。

### 2.3 金庫門分頁的互動細節

這輪 grilling 之前先去讀了 `FileLocker_技術規格文件.md` 第 21 節「資料夾防護」的既有機制（唯讀查證，不是猜測），確認幾個跟信封本質不同的地方，直接影響這輪的決策方向：

- 上鎖／解鎖目前分兩條路：**右鍵選單觸發的走原生 WPF 小視窗**（`FolderGuardConfirmLockWindow`／`FolderGuardUnlockPromptWindow`，刻意不透過 WebView2，避免為了一個右鍵確認動作啟動整個 WebView2 環境），**只有 App 內「資料夾防護」分頁是 WebView2/Vue 畫面**。
- 分頁本身已經有「新增資料夾」按鈕，可以直接發起新的上鎖，不是只能靠右鍵選單。
- 上鎖本身**不需要密碼**、是近乎瞬間完成的 ACL 操作（不像加密要花時間寫入 Vault），解鎖才需要驗證身份。
- 解鎖後的資料夾**留在清單裡**（可「前往資料夾」或「再次上鎖」），不會像信封解密後那樣離開清單——兩者清單語意不同：信封清單記錄「加密過的檔案」，解密後不再符合這個狀態理應離開；資料夾防護清單記錄「持續管理中的資料夾」，上鎖或解鎖都還是同一批要繼續管理的資料夾。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 金庫門動畫的適用範圍 | **只用在 App 內「資料夾防護」分頁，不動右鍵選單觸發的原生 WPF 小視窗** | 那兩個原生視窗是刻意不透過 WebView2 的既有架構決策，硬套動畫等於推翻這個決策，範圍會從「畫面美化」變成「原生視窗架構改動」 |
| 分頁內新增資料夾／再次上鎖要不要額外確認彈窗 | **不需要**，選定資料夾／按下按鈕本身就是明確意圖 | 右鍵選單需要確認彈窗是為了防止滑鼠移動中誤觸；App 分頁裡「新增資料夾」要先跳系統資料夾選取器、明確選一個資料夾，這一連串操作本身已經是刻意動作，金庫門的關閉動畫本身就是最好的即時回饋，不需要再疊加一層彈窗 |
| 清單常態（沒有動畫播放時）的呈現 | **輕量化**：欄位順序**轉盤－資料夾路徑－狀態－解鎖按鈕**，不是每列都畫完整立體金庫門 | 金庫門是立體、有厚度感的物件，硬要壓扁成一列會失去重量感、也不好辨識（不像信封本來就是扁平的紙）；資料夾防護操作性質比加密輕量，清單常態也該輕量，金庫門的視覺重量感留給「動作發生當下」集中呈現 |
| 轉盤在清單列的角色 | 轉盤是**持續顯示的小圖示**（取代通用鎖頭圖示），**可以直接點擊，效果等同按下「解鎖」按鈕** | 把「金庫」的視覺識別（轉盤造型）壓縮進清單常態的輕量圖示裡，不需要額外疊加畫面 |
| 點擊轉盤（或按解鎖按鈕）的完整互動時序 | ① 點擊轉盤：**小幅轉動立刻彈回**（驗證還沒過的即時觸感回饋，只有直接點轉盤才有這一步）② 跳出密碼／Passkey 驗證 ③ 驗證成功後，**轉盤才真正完整轉一圈**——**只有轉輪動，不牽動門扇／框架** | 呼應「轉開保險箱」的物理直覺：先摸一下試試看（immediate feedback），真正打開要等驗證通過。清單列本來就只常態顯示轉輪（見上一列），解鎖動作的完整動畫延續同一個視覺元素，不無中生有帶出門扇跟框架——完整的金庫立體場景（框架＋門扇＋轉輪）保留給下方〈2.4 新增資料夾的開門儀式〉那個獨立情境 |
| 觸發方式是否影響完整轉一圈動畫要不要播 | **不影響**——不論從轉盤或「解鎖」按鈕觸發，驗證成功後完整轉一圈都會播 | 完整旋轉代表「狀態真的改變了」這個事實本身，不是點擊方式的專屬獎勵；只有「小幅回彈」前導動作才是直接點轉盤才有的額外回饋 |
| 「再次上鎖」（relock，既有已解鎖列，不需要密碼）要不要播動畫 | **要**，播一段**反方向**的完整轉輪旋轉，點下去立刻播（不用等後端回應——後端本來就是 fire-and-forget，沒有可以等待的結果） | 跟解鎖的正向完整旋轉做出方向上的區隔，讓「解鎖」跟「上鎖」兩個語意相反的動作不會共用同一種「轉一圈」觀感而分不清楚剛剛發生了什麼；不需要密碼，也就沒有「先小幅回彈等驗證」這個前導階段，直接播完整動畫 |
| 「解鎖全部」時，多個轉盤怎麼一起播放解鎖動畫 | **依序錯開**（由上到下，間隔 80-120ms 開始轉），不是全部同時轉。後端 `FolderGuardService.UnlockAllAsync` 目前只回傳單一聚合結果，沒有逐筆進度事件（探索階段已查證），這個錯開效果**這輪只做前端假的**：觸發批次解鎖前先記住當下所有「已鎖定」的路徑清單，後端回傳整批成功後，前端自己用 `setTimeout` 依序播放清單裡這些列各自的完整轉動，全部播完才真正重新整理列表 | 多個轉盤同時動作視覺上是一團混亂的旋轉；依序錯開的小延遲讓眼睛自然跟著節奏往下看，畫面更有秩序，也呼應金庫門這種帶儀式感的操作。不改後端是這輪明確的範圍決定——真正的逐筆後端事件屬於未來如果要做「即時反映哪一筆卡住／失敗」才需要的東西，這輪批次操作本身就是全有全無，沒有這個需求 |
| 轉輪停到定位時要不要有「喀」一聲卡住的回彈手感 | **要**：轉盤用先加速、持續減速、到定位前衝過頭一點點再彈回卡住的動態，不是線性轉到底就停 | 呼應「漸漸變慢＋最後頓一下」的物理直覺；用 CSS `@keyframes` 分段控制速度曲線達成，細節（含調參數時踩過的坑）記在《GUI造型探索_技術規格.md》 |
| 轉輪最終停等角度 | 必須是 **90° 的整數倍** | 轉盤本體是四個握把、四等分的造型，停在任意角度會讓握把跟門框/外殼的相對位置歪掉、視覺上不對稱；90° 的倍數保證每次停下來造型都是正的 |
| 開鎖／上鎖兩個方向的轉輪速度曲線要不要一樣 | **不用完全一樣，但收尾都要乾脆俐落**——共用同一條收尾曲線形狀，靠時長跟轉的圈數區分兩個方向的手感，不是靠曲線形狀本身區分 | 開鎖是「解開束縛」、上鎖是「扣上收尾」，語意不同，時長跟圈數的差異已經足夠讓兩者播起來能感覺出差異；曲線形狀本身反而是收尾「乾不乾脆」的關鍵 |
| 解鎖後資料夾要不要離開清單 | **留在清單裡**，維持既有行為（可再次上鎖或前往資料夾） | 資料夾防護清單記錄的是持續管理中的資料夾，跟信封「已加密清單」的語意不同，不能套用信封那套「解密後離開清單」的邏輯 |

### 2.4 清單常態圖示的狀態區分

清單列常態顯示的轉輪圖示（見〈2.3〉「清單常態的呈現」「轉盤在清單列的角色」），已鎖定跟已解鎖兩種狀態用**同一套顏色（`--tint-guard` 系列既有 token，不新增顏色 token），靠轉輪角度／透明度做區分**，不做成兩種色階。理由：資料夾防護清單本來就已經有純文字的狀態欄位（`folderGuard.statusLocked`／`statusUnlocked`）並存，轉輪圖示的角色是「可點擊的視覺化鎖頭」，不是唯一的狀態指示來源，不需要為了圖示本身再疊加一組新的顏色語言；同一套金色（`#A8770F` 系列，跟信封蠟封敘事的呼應色一致）維持整個資料夾防護頁面的色彩一致性。

### 2.5 新增資料夾的開門儀式

這是先前從未定案過的空白——〈2.3〉只講了「轉輪單獨旋轉」用在解鎖／上鎖，完整的立體金庫場景（框架＋門扇＋轉輪）究竟何時出現，之前沒有問到。這輪確認：**完整開門／關門動畫只用在「新增資料夾」這個流程**，不是解鎖既有項目的一部分。

完整流程：

1. 使用者按下「新增資料夾」按鈕。
2. 畫面疊一層**全螢幕懸浮金庫層**，背景加模糊（`backdrop-filter: blur()`），呈現一座**關閉狀態**的完整金庫（框架＋門扇＋轉輪）。
3. 播放開門動畫（轉輪旋轉→門扇打開，接力時序，沿用〈2.2〉既有的 CSS 時序常數）。
4. **門完全打開之後**，才彈出 Windows 原生「選擇資料夾」對話框。
5. 使用者選定資料夾，或按取消。
6. 不論選定或取消，都播放**完整的關門動畫**（門扇關上→轉輪轉回去，接力反向）。
7. 關門動畫播完，懸浮金庫層才消失。
8. 若使用者確實選定了資料夾：**不需要密碼、立即自動保護**，該資料夾馬上以「已鎖定」狀態出現在清單裡——沿用第 1 節既有定案的「新列進場：滑入＋推擠，轉盤同時反方向旋轉、阻力遞增、最後卡進定位有頓挫感」那套既有動畫，這裡不是重新設計一套新的進場方式，是接續在懸浮金庫層消失之後發生的下一段。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 開門動畫跟 Windows 選資料夾視窗的時序關係 | **門開完才彈選資料夾視窗** | 因果關係最直白——「開了金庫門才能進去選東西」，動畫語意跟操作順序一致 |
| 選定／取消後金庫怎麼收場 | **播完整關門動畫才消失**，選定跟取消走同一套收場方式，不因結果不同而有差異視覺 | 開跟關要對稱，才不會「開門很隆重、關門悄悄消失」這種頭重腳輕的觀感；取消不代表操作異常，不需要額外的錯誤/警告視覺 |
| 新增後要不要額外確認才正式保護 | **不需要，選完就自動保護、立刻顯示已鎖定** | 對應資料夾防護「上鎖不需要密碼、近乎瞬間完成」的既有性質；選擇資料夾這個動作本身已經是明確意圖，疊加一層確認彈窗只是重複詢問 |
| 懸浮金庫層的呈現方式 | **背景模糊＋全螢幕疊層**，不是塞進表格某一格或讓某一列的高度撐開 | 這是全新的「新增」動作，跟清單裡任何一個既有項目都無關，不該從某一列的位置長出來；背景模糊讓場景維持 mockup 驗證過的原始比例（320×280 或更大），不需要為了塞進小空間重新設計縮小版素材 |

### 2.6 素材遷移方式

`Vault_Wheel.svg`／`Vault_Door_Slab.svg`／`Vault_Frame.svg` 目前只存在於 repo 根目錄的 `assets/` 資料夾，`src/FileLocker.Web/src/assets/` 裡還沒有。這輪決定**直接複製原始檔案**過去，不重新設計或匯出縮小尺寸的版本——mockup（`10-vault-door.html`）已經驗證過的比例、線條粗細直接沿用，懸浮金庫層本身就是全螢幕疊層，不受限於清單欄位的小尺寸，沒有另外做一套「小尺寸專用素材」的必要。

### 2.7 減少動畫（`prefers-reduced-motion`）處理範圍

目前整個 `FileLocker.Web` 專案**沒有**處理 `prefers-reduced-motion` 這個使用者偏好設定的既有機制（探索階段已查證，非猜測）。這輪範圍限定：**只在這次新增的金庫門相關 CSS 動畫**加上 `@media (prefers-reduced-motion: reduce)` 保護——轉輪旋轉、開門／關門動畫，在這個偏好開啟時全部改成一段短暫的淡入淡出（`opacity`，約 150-200ms），不做旋轉或位移；Windows 原生「選擇資料夾」對話框本身不受影響，維持系統原生行為。

App.vue 裡既有的其他動畫（modal 淡入淡出、`table-row-in` 清單進場等）這輪**不**一併補上 `prefers-reduced-motion` 保護，列入〈7.2 待辦事項——資料夾防護（金庫門）〉，之後要對全站動畫做一次盤點時再一起處理，不在這輪金庫門範圍內。

## 3. 側欄與票根清單

### 3.1 背景

這輪探索的起點是使用者想重新檢視 `7-claim-ticket.html`（v2-7「認領票根風」）這個方向的殼子風格——側欄導覽、米白/brass 的色調。`7-claim-ticket.html` 本身在信封蠟封方向定案時就已經被記錄為「跟信封蠟封概念相近但只做了清單頁一頁」的早期、未打磨的探索品，信封蠟封方向定案後這條路線一度被放下，沒有繼續往下做。這輪重新把它撿回來，但範圍縮小、目標明確：

**這輪明確要求不要延續 `7-claim-ticket.html` 本身的未打磨版型，改在 `12-file-tab-merged.html`（已經打磨過的清單列樣式）的基礎上調整**，郵戳徽章的尺寸／文字擺放則照抄 `9-envelope-list.html` 的既有作法。所有調整都彙整進單一新檔案 `13-sidebar-ticket-shell.html`，經過十輪左右的來回調整。

### 3.2 路線分工

上一輪留下的疑慮——票根圖示列的互動邏輯跟〈1.7 信封清單虛線的互動〉那節幾乎是同一套（點擊→小幅撕開的即時回饋→驗證→驗證通過整個撕開→停留→飛走→下面補位），視覺造型卻不同——這輪已經定案，不是二選一，是**兩套視覺分別對應不同的操作情境**：

| 情境 | 視覺方向 | 對應 mockup |
|---|---|---|
| **加密流程**（新增檔案、選擇要加密的內容、加密表單本身） | 信封蠟封 | `8-envelope-assembled.html`（折疊/寄出動畫）、`12-file-tab-merged.html`（新增檔案信封彈出表單） |
| **已加密的檔案清單**（清單列本身、解密/驗證觸發） | 票根撕邊 | `13-sidebar-ticket-shell.html` |

第 1 節裡已經寫定的「加密表單信封彈出」「批次多張信封疊在一起」「寄出動畫（信封往深處飛走）」這些跟信封形狀本身綁定的決策**維持有效，不作廢**——它們對應的是加密流程本身（把檔案「寄」進金庫的動作），跟票根視覺負責的清單頁是兩個不同的畫面、不衝突。

**分頁合併後的正式名稱定案為「加密」**（不是先前暫稱的「檔案」）——已同步更新到第 1 節。

互動邏輯（撕開/點擊→即時回饋→驗證→完整動作→飛走補位）兩套視覺共用同一套設計語言是刻意的——使用者的操作心智模型（先摸一下、驗證、再看到完整動作）在兩個情境下應該一致，只是外殼造型按情境切換（加密用信封，清單用票根撕邊），不是各自發明一套不同的手感。

### 3.4 票根清單列

#### 圖層結構

一列（`.ticket-wrap`）由外而內：

- `.ticket-wrap`：負責「這一列在清單裡占多少垂直空間」，平常不設高度限制、不裁切，讓內容（含換行文字）自然撐開；只有真的要收合讓下面的列補位時，才由 JS 暫時鎖住高度當收合動畫起點（細節見《技術規格》）。
- `.ticket-stage`：負責「這一列要不要整個往旁邊飛走」的位移/淡出。
- `.ticket`：真正看得到的卡片本體（白底＋邊框＋圓角），裡面放：
  - `.ticket__seal`：一個 `<button>`，是「圖示＋撕邊」的組合，貫穿整張卡片的可視高度，是撕開動作唯一的觸發熱區。
  - `.info`／`.postmark-slot`／`.actions`：檔名/中繼資料、狀態郵戳徽章、操作按鈕。

#### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 撕邊方向 | 垂直，不是水平 | 使用者明確要求「撕邊是要直的」，對應真正票根騎縫線的方向 |
| 撕邊要不要貫穿整張卡片 | 要，從卡片可視的上邊緣到下邊緣，只留卡片自己的內距（10px）當緩衝 | 使用者要求「橫跨整個清單列的欄位」「像真正的票根一樣」；技術上靠讓 `.ticket__seal` 用 `position:absolute` 直接掛在 `.ticket` 上（不受卡片自己 flex 排版的內距限制）達成，見《技術規格》 |
| 圖示跟撕邊的關係 | 圖示疊在撕邊正中間，像貼紙/火漆貼在騎縫線上 | 使用者明確要求；也讓「點圖示」跟「點撕邊」變成同一個熱區，不用另外處理兩種觸發來源 |
| 圖示形狀 | 圓形，帶邊線（邊線顏色跟圖示識別色一致，不是統一灰色） | 使用者詢問過意見：沒有邊線的色塊看起來像印刷上去的，不像「貼上去」的東西；加了邊線更像蠟封/貼紙，呼應這個專案本來就在用的信封蠟封語彙 |
| 圖示尺寸 | 32px（比最初嘗試的 38-40px 縮小） | 圖示太大會讓貫穿全高的撕邊看起來像兩根短短的裝飾線（使用者形容「蟑螂鬚」），縮小圖示才能讓撕邊有足夠的可見長度 |
| 點擊觸發後的完整互動時序 | ①點擊：撕開動畫的最前面一小段（極小幅度，不是另一個獨立動作）②停等 1 秒（正式版這裡是密碼／Passkey 驗證彈窗，這輪只是單純等待）③驗證通過：完整撕開，兩邊（含卡片本身的白底/邊框）真的裂成兩半，各自留有自己的撕線 ④停留一下 ⑤整列（已撕開的兩半合成一個單位）往旁邊飛走、淡出 ⑥下面的列往上補位 | 跟金庫門轉盤同一套設計語言（先給即時回饋、驗證通過才播完整動作）；「一小角」直接複用完整撕開的機制、只是縮小位移跟時長，確保跟後面接續的完整撕開是「同一個動作的延續」，不是切成兩段不相干的東西；飛走＋補位沿用〈1.7 信封清單虛線的互動〉已經定案的收尾邏輯 |
| 撕開範圍要不要包含卡片本身（白底/邊框） | 要，不是只有文字內容飄在卡片上面裂開 | 使用者明確要求；技術上把整張 `.ticket`（含背景/邊框）複製成兩份裁切顯示，不是只複製內部文字 |
| 撕開後兩邊要不要都看得到撕線 | 要，兩邊各自有一條完整的撕線，不是共用一條線被攔腰裁成兩截 | 原本共用一條線裁在正中央，裁完常常整條線的可見像素都分到同一邊，另一邊完全看不到；改成兩邊的撕線各自往自己那一側偏移，撕開的裁切邊界左右各留出完整一條線的空間 |
| 動作按鈕的顏色 | 全部統一成白底外框，不特別標示「主要」按鈕 | 每一列實際開放的按鈕數量不固定（1 顆或 2 顆），如果金色實心只套用在其中一顆，那顆金色按鈕在畫面上的左右位置會隨列而變、看起來像色塊亂跳；統一成同一種樣式反而比較不亂 |
| 郵戳徽章（找不到指標檔／巢狀鎖定）的樣式 | 直接照抄 `9-envelope-list.html` 的尺寸（56px 圖示＋文字並排）跟固定寬度欄位做法 | 使用者明確要求；郵戳圖示本身沿用既有素材 `Postmark_Warning.svg`／`Postmark_Nested_Lock.svg`，不重畫 |
| 郵戳徽章的水平位置 | 固定，不隨旁邊按鈕數量變動 | 使用者明確要求；技術上給動作按鈕欄位固定寬度（180px）＋靠右對齊，不管按鈕數量多寡，郵戳欄位前面的空間都一致，這點也是照抄 `9-envelope-list.html` 已經處理過的同一個問題 |

#### 技術細節（實作時可以直接沿用的做法，不用重新推導）

- **撕開效果的實作方式**：`.ticket__seal` 觸發時，JS 把當下這一列唯一互動層 `.ticket` 整份 `cloneNode(true)` 兩份，分別加上 `.ticket__half--left`／`--right`，用 `clip-path: inset()` 各自只露出撕線左右兩側（裁切點用 JS 即時量測 `.ticket__seal` 的實際中心點 `offsetLeft + offsetWidth/2`，不是猜一個寫死的 px 值）。平常兩份疊在原本的 `.ticket` 上面、opacity:0，看起來就跟只有一份一樣；撕開時原本的 `.ticket` 淡出、兩個半邊淡入並往外 `translateX`+`rotate`，看起來像真的裂開。
- **撕邊要貫穿整張卡片、不受卡片自己 padding 限制**：關鍵是讓 `.ticket__seal`（連同裡面的撕線）用 `position:absolute` 直接掛在 `.ticket`（`position:relative`）上，`top:0;bottom:0`——absolute 子元素的 top/bottom 是相對容器的 padding box 量，不會被 `.ticket` 自己的 flex 排版跟內距影響。踩過的坑：一開始撕線容器（`.ticket__seal`）還是普通 flex 子元素、靠 `align-self:stretch` 撐高，撐出來的高度只跟旁邊文字內容一樣高（雙行文字約 39px），圖示本身 32px 置中疊上去之後幾乎整個容器都被圖示的白底圓圈蓋住，撕線技術上「有畫」但完全看不見——不是顏色對比度問題（一開始誤判成對比度問題，調過顏色沒解決，後來才找到真正原因）。
- **兩邊撕線各自完整可見**：`.ticket__half--left .ticket__tear-line{left:calc(50% - 2px)}`／`.ticket__half--right .ticket__tear-line{left:calc(50% + 2px)}`，讓兩邊的撕線各自落在自己那一側裁切邊界內側 2px，撕開時才不會被 `clip-path` 邊界正好切成兩段各自只剩一半可見。
- **收合／飛走動畫不能同時做**：整列收合（`max-height` 轉場）跟飛走位移（`translateX`）如果同時疊加，`overflow:hidden`（收合必須要有，否則沒辦法把高度平滑收到 0）會把還在飛的內容攔腰裁掉，看起來像卡到外面去。解法是嚴格分兩個階段接續播放，不重疊：先播完飛走＋淡出（此時 `.ticket-wrap` 完全不設 `overflow`/`max-height`，畫面上想飛多遠都不會被裁），確認飛走動畫真的播完（畫面上已經看不到任何東西）之後，才用 JS 量測當下 `scrollHeight` 當起點，開始收合高度動畫。
- **郵戳徽章固定寬度欄位**：`.postmark-slot{width:90px}` 是獨立欄位，`.actions{width:180px;justify-content:flex-end}` 讓按鈕數量變化只影響按鈕在欄位內部靠右的起始位置，不影響欄位本身的寬度——這樣郵戳欄位前面可用的空間才會固定，不會因為隔壁 `.info`（`flex:1`）欄位吸收/釋放空間而跟著飄移。

## 4. 密碼庫筆記本方向

### 4.1 背景

信封（加密/清單/解密）、金庫門（資料夾防護）兩個方向定案後，密碼庫這輪延伸第三種視覺語彙——原因是密碼庫的操作性質（查閱、記錄、翻找）跟前兩者完全不同：信封是「裝東西寄出」、金庫是「限制空間進出」，密碼庫則是「持續查閱/記錄的筆記」，硬套前兩者的比喻都不合適，需要獨立的語彙。

密碼庫實際功能結構（`packages/password-locker-ui/src/PasswordLockerPage.vue`）：兩個分類（`Website` 網站帳密／`EncryptedFile` 已加密檔案）、每筆帳密可選配 TOTP（既有一組圓環倒數邏輯 `totpRingStyle`）、可關聯多個網域、有搜尋/排序、新增編輯表單。這份文件記錄跟使用者討論筆記本方向時，一輪一輪來回調整、邊討論邊畫的決策脈絡。

### 4.2 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 密碼庫的視覺語彙 | **筆記本**（螺旋線圈裝訂＋橫線內頁） | 密碼庫是查閱/記錄性質，跟信封「寄出」、金庫「限制進出」的動作性質不同，需要獨立的第三種語彙 |
| 整體容器要不要畫成闔上的封面 | **不要，直接用打開的內頁**（螺旋線圈＋米白橫線紙，中性色） | 最早畫過深咖啡皮革封面（含「PASSWORD NOTES」字樣），但深色封面當整頁背景，跟上面要疊的搜尋框/清單/表單這些高資訊密度控制項對比不夠、可讀性有風險；米白橫線內頁淺色、對比度好，撐得住功能性 UI；封面上烤死的英文字也違反雙語規則（所有文字要走 `t('key')`），標題交給前端疊字 |
| 內頁橫線的附帶用途 | 如果清單列高度跟橫線間距一致，**清單分隔線可以直接借用橫線本身**，不用另外疊 CSS `border-bottom` | 避免「畫一個筆記本樣子的背景」+「另外浮一層普通表格」這種兩張皮的違和感 |
| 兩個分類的顏色 | **網站帳密＝黃銅金（沿用主色）／已加密檔案＝深綠（新增）** | 黃銅金是整個 App 已定案的主色（信封邊框、蠟封、金庫轉輪都用），密碼庫沿用其中一色能維持同一個 App 家族的觀感；深綠是傳統帳本／分類帳常見的封面色，跟黃銅金搭配有典故（老式帳本綠皮+燙金）。橘色被排除：跟既有暗紅蠟封（警告/找不到指標檔的語意色）在色輪上太接近，容易造成語意混淆；藍色被排除：完全是外來色，跟信封/金庫的暖色調世界脫節 |
| 分類標籤選中/未選中狀態 | **不另外畫圖檔**，選中＝往外凸出、飽和度拉滿、陰影加深；未選中＝往內收、降低飽和度——都用 CSS `transform`／`opacity` 處理 | 位置/陰影/透明度差異用程式碼就能做出來，畫兩套圖檔是不必要的重複工作 |
| 密碼顯示/隱藏的圖示 | **維持現有的通用眼睛圖示，不套用筆記本主題**（便利貼提案已撤回） | 便利貼縮小到清單列的實際尺寸後辨識度不夠，「點一下掀便利貼＝看密碼」也不夠直覺；眼睛圖示是幾乎所有軟體通用的強慣例，使用者已有肌肉記憶，不是每個小圖示都要塞進筆記本比喻裡，比喻只適合套在撐得起細節、或沒有強烈既有慣例的地方 |
| TOTP 倒數怎麼呈現 | ~~沿用既有圓環邏輯（`totpRingStyle`），疊在懷錶造型錶面外圈~~——**這條已被下一輪修正取代，見下一列** | 圓環已經是驗證過可讀性的既有實作，換皮不換邏輯風險最低；指針掃動要另外寫「角度隨時間更新」的邏輯，且指針視覺上比圓環更難一眼判斷剩餘比例 |

| TOTP 驗證碼數字本身要不要顯示 | **要**，獨立一個固定寬度欄位顯示三碼一組的數字（例如「482 913」），不是只有扇形/圓環這個時間指示器 | 上一輪決策記錄只定案了「剩餘時間怎麼呈現」，沒有涵蓋「驗證碼本身的數字要不要顯示」這件事——這輪實作 mockup 時使用者發現這個缺口：只看到轉圈圈的視覺，看不到真正要複製的驗證碼。三碼一組（不是六碼連在一起）是跟簡訊驗證碼／Authenticator App 一致的既有排版慣例 |
| 懷錶錶面的刻度數量 | **12 個粗刻度，不加細**（曾經畫過更細緻的刻度版本，最後放棄） | 這個元素實際顯示尺寸不大（清單列旁邊的小圖示，約 32-48px 量級），刻度太細縮小後會糊成一片；圓環本身已定案平滑不分段，刻度純粹裝飾，沒必要為了裝飾犧牲小尺寸下的清晰度 |
| 新增帳密的入口素材 | **鋼筆**（不是鉛筆），白／珍珠光澤筆身＋兩圈金色裝飾環（筆蓋、握筆處各一圈）＋金屬筆尖 | 最早畫過木紋筆身配金屬鋼筆尖的版本，材質語言矛盾（木頭鉛筆不會裝金屬鋼筆尖）；後改成滑順珍珠光澤筆身解決材質矛盾；加上兩圈金色裝飾環是為了跟其他素材的黃銅金主色調牽上關係——這是目前素材庫裡唯一一個底色是冷色系（白/銀）的素材，金色裝飾環讓它不會顯得像來自別的 App |

## 5. 信封加密流程接入側欄殼子

### 5.1 背景

〈第 3 節 側欄與票根清單〉已經定案側欄殼子（`13-sidebar-ticket-shell.html`）跟票根清單列，但那份 mockup 裡點擊「加密新檔案」目前沒有任何動作——完整的信封加密流程（新增檔案彈出信封、選檔案、設密碼/Passkey/恢復金鑰、闔上蓋章、完成）都還停留在獨立的 `12-file-tab-merged.html`（排版驗證用，未接動畫）跟 `8-envelope-assembled.html`（動畫細節驗證用，未接側欄殼子）兩份各自獨立的 mockup 裡，沒有整合成一份可以從頭走到尾的完整示範。

這輪的目標：把整個信封加密流程接進 `13-sidebar-ticket-shell.html`，並補上這個流程裡先前一直沒有規劃過的一塊空白——加密時如果選了恢復金鑰，金鑰產生後要怎麼呈現給使用者——同時加上深/淺色切換，方便使用者直接檢視視覺效果正不正常。

信封本體的彈出/開合/選檔案排版技巧已經在 `12-file-tab-merged.html` 驗證過（`.dropzone`／`.sheet`／`.envelope-outer` 等），這輪直接複製沿用，不重新設計；金庫門動畫已經是這個殼子裡「資料夾防護」分頁的既有實作，不受這輪影響。

### 5.2 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 這輪要不要把「恢復金鑰顯示畫面」的視覺造型一併設計進去 | **要**，跟整個加密流程一起做 | 這是先前討論信封蠟封、側欄票根、密碼庫筆記本三輪都沒有涵蓋到的空白——現有 `App.vue` 裡 `recoveryKeyDisplay` 彈窗雖然功能上已經存在，但視覺上一直是最原始通用的 `.modal-overlay` 樣式，沒有套用任何一輪新視覺語言；剛好這輪要做完整加密流程示範，一起補上 |
| 恢復金鑰畫面的視覺風格 | **信封主題化，當成加密儀式的最後一步**，不走中性風格 | 跟密碼庫設定頁「維持中性、不套主題」的判斷標準不同——密碼庫設定頁是高頻率操作的功能性頁面，恢復金鑰畫面是加密流程裡只會出現一次的儀式性尾聲，適合延續信封敘事，不是每個功能性畫面都要套主題，但這個畫面的敘事位置適合 |
| 恢復金鑰畫面具體怎麼呈現 | **比照已選檔案清單那張「從信封下緣冒出來的白紙卡片」（`.sheet` 手法，見《GUI造型探索_技術規格.md》相關章節），不新增素材** | `.sheet` 是純 CSS 做的紙卡容器（背景色/圓角/陰影），不是額外的 SVG 貼圖——技術上直接複用同一個容器語言，金鑰字串就是卡片上的文字內容，不需要另外請人畫新素材 |
| 金鑰紙卡出現的時機 | **信封闔上＋蜜蠟蓋章的收尾動畫播完後，緊接著自動出現**，不等使用者額外點選 | 蓋章闔上是「信封封好了」這個動作的完成訊號，金鑰紙卡緊接著冒出來，讀起來像「順便附上一張重要的附件，別忘了拿」，跟蓋章動畫是同一段儀式的延續，不是切成兩個不相干的段落 |
| `.sheet` 紙卡的進場動畫 | **兩段式動作**：①卡片從信封底下（被信封擋住、看不見的地方）往下滑出，滑到整張卡片完全露出、看得到全貌 ②接著反過來往上移動，一路移動到卡片最終落在信封本身的可視範圍內（卡片跟信封視覺上重疊，不是浮在信封下方空白處）——不是原本的「瞬間出現、沒有過渡」，也不是單純的「往下滑出＋淡入」 | 使用者明確指出現行的已選檔案清單卡片點擊後沒有任何過渡直接冒出，體驗生硬；兩段式的「先抽出來、再收回去疊上信封」比單純的單向滑入更貼近「從信封裡拿出一張紙」的實體動作直覺（抽出來要先看到全貌，收回去疊放才是最終定案的休止位置）。**這個修正回溯套用到已選檔案清單那張卡片，不是只有恢復金鑰這張新卡片才有**——兩張卡片使用同一個容器語言，進場動畫也該一致，不能只改新的、放著舊的不管。動畫曲線傾向使用 `cubic-bezier(0.32, 0.72, 0, 1)`（iOS 風格抽屜曲線，接近 apple-design skill「Drawer/sheet」情境建議的彈簧手感），不引入 JS 彈簧動畫函式庫——這是一次性、觸發後播到底的動畫，沒有使用者持續拖曳/隨時可能被打斷的情境，CSS 曲線已經足夠 |
| 恢復金鑰紙卡要不要能點外面取消 | **不行**，維持跟現有 `App.vue` 裡 `recoveryKeyDisplay` 彈窗一樣的規則——必須按明確的「已存檔/關閉」按鈕才能關掉 | 這是一次性金鑰揭露畫面，點外面不小心關掉、金鑰又沒地方找回來，後果是永久遺失資料存取權；點外面即時取消跟疊層模糊漸變那輪（見 `App.vue` 裡 7 個彈窗補上點外面取消的批次）已經明確排除了這一類一次性金鑰揭露畫面，換了視覺造型不代表規則跟著鬆綁 |
| 步驟二（密碼／Passkey／恢復金鑰勾選）表單要放在信封輪廓裡面還是另外用 `.sheet` | **步驟一、二各自獨立判斷**：步驟一（選檔案清單）內容多、已經定案用 `.sheet`；步驟二欄位比 `8-envelope-assembled.html` 原本驗證過的簡單密碼欄位多很多，如果排版塞得下信封可視輪廓內就放裡面（比照 `8-envelope-assembled.html` 的 `.form-zone`），塞不下才跟步驟一一樣用 `.sheet` | 「信封可視輪廓能放多少內容」是排版問題，兩個步驟的欄位數量本來就不一樣，沒有理由預設兩步都要用同一種容器；哪一種可行留給實作階段實際排版、量測之後決定，不是這輪能憑空判斷的事 |
| 深色模式下信封本身怎麼處理 | **信封素材維持原色，不跟著深色化** | 信封素材（`Envelope_Body.svg` 等）目前沒有深色版本（不像筆記本已經有 `Notebook_Body_Drack.svg`）；跟密碼庫分類標籤/懷錶「沒有專屬深色素材就不強求」是同一個判斷原則——米白/牛皮紙色的信封在深色外殼上仍然讀得出是一個信封，只是沒有跟著整體氛圍變深，之後如果要做深色版信封素材，屬於下一輪的待辦，不是這輪的範圍 |
| 深/淺色切換的做法 | **沿用 `14-notebook-in-shell.html` 已經驗證過的測試按鈕機制**（標題列一顆 ☀/☾ 圖示按鈕，切換 `data-theme`），不重新設計一套 | 這個切換鈕本來就是明確標註「測試用，不代表正式殼子要加這顆按鈕」的臨時驗證工具，兩輪 mockup 共用同一套機制最省事，也不需要另外決定新的視覺 |

## 6. 已知限制（依主題分組）

### 6.1 資料夾防護（金庫門）

- 「解鎖全部」的錯開動畫是前端自己模擬（記住觸發前的鎖定清單，成功後用 `setTimeout` 依序播放），後端沒有真正的逐筆進度事件——如果某一筆解鎖實際上失敗（目前後端是整批全有全無，理論上不會發生單筆失敗），前端播放的錯開動畫仍然是「假設全部都成功」的樂觀呈現，不會反映真實的逐筆狀態。
- 懸浮金庫層的背景模糊（`backdrop-filter`）在極舊版 WebView2/Chromium 核心下可能不支援或效能不佳，這輪沒有另外規劃降級方案（沒有測試環境驗證這個風險是否存在）。

### 6.2 側欄與票根清單

- `.ticket__half`（撕開時顯示的兩個半邊）是整份 `.ticket` 的 DOM clone，每一列在頁面載入時就會多出兩份幾乎一樣的 DOM——這輪清單只有 6 列，效能上沒有感覺，但如果之後清單筆數很多（例如上百筆），這個「每列預先複製兩份」的做法要重新評估，可能要改成撕開當下才動態建立 clone、播完就移除，不要整份清單一次全部預先複製。
- 撕線在批次加密（`--brass-tint` 底色）那一列用了不同的顏色覆蓋（`var(--brass-deep)`），其餘列統一用 `var(--ink-faint)`——這是手動個別覆蓋，不是自動依底色算對比度，如果之後又有新的底色變化（例如深色模式），需要重新手動確認每一種底色情境下撕線的對比度還夠不夠。
- 收合側欄的 hover 提示（tooltip）只是先示意的簡化版本，沒有處理視窗邊緣被截斷、鍵盤 focus 時要不要也顯示提示等細節。

### 6.3 信封加密流程接入側欄殼子

- 這輪範圍限定在**加密流程**（新增檔案→選檔案→設密碼/Passkey/恢復金鑰→闔上蓋章→完成→恢復金鑰畫面）——不包含解密/清單列本身的撕開互動（那是 `13-sidebar-ticket-shell.html` 已經做過的既有示範，這輪不重新處理），也不包含批次加密（多個檔案疊在一起的信封堆疊視覺）。
- 信封素材沒有深色版本，深色模式下會有「殼子深、信封本身仍是淺色」的視覺落差，這是刻意接受的取捨，不是遺漏。
- 恢復金鑰畫面這輪只定案視覺呈現方式，不處理「使用者關掉這個畫面之後，清單列要不要播放新增項目的進場動畫」這類接續細節——留待實作時如果有明顯的排版/動畫銜接問題再回頭補記。

### 6.4 獨立解密流程（信封＋Sheet）

- `readLockedFileMetadata`（唯讀中繼資料）這個新訊息的確切欄位／回傳格式（是否包含檔案大小、是否複用既有 metadata 結構）這輪沒有細部設計，只定案了「要有這個訊息、不需要密碼」的概念。
- sheet 內部左右滑動翻頁的精確時長／easing 曲線沒有定案數值，只定了動態概念，比照〈5.2〉抽出動畫傾向的 `cubic-bezier(0.32, 0.72, 0, 1)` 是否也適用於翻頁，還沒驗證過。
- Passkey 驗證失敗時 sheet 上顯示的提示文案，這輪只定了「要有提示」，確切文字（雙語）沒有寫。

## 7. 待辦事項（依主題分組）

### 7.1 信封蠟封方向

- 密碼庫、設定頁要不要也給一個衍生的視覺語言，或維持跟其他方向共用的中性風格——這次沒有問到，下一輪要延伸整個 App 時需要再定案。**後續進度**：密碼庫已在第 4 節獨立定案（筆記本語彙），設定頁仍未定案。
- 「新增檔案」按下後彈出的信封，跟〈1.8「寄出」動畫與加密交易模型〉那節定義的「信封怎麼出現（開場）」是不是同一套動畫（垂直落下＋回彈＋順勢打開）——邏輯上應該是同一套，但沒有明確問過，先假設是同一套，之後如果行為不一樣要回來修正這條。mockup（`12-file-tab-merged.html`）目前用的是簡化過的 scale+fade 進場，不是完整版。
- 步驟一「取消」按鈕的確切行為（放棄新增退回清單、還是清空已選檔案？）沒有定案，見〈1.6〉決策記錄表最後一列。
- 分頁名稱暫稱「檔案」的實際文案問題——**已解決**：分頁名稱已在第 3 節定案為「加密」。
- `pending`/`committed` 狀態欄位的確切 schema（欄位名稱、序列化格式）還沒定案，只定了概念。
- 批次加密其中一個檔案 finalize 失敗（例如刪除原始檔失敗）時，其餘檔案要不要繼續 finalize、還是整批一起卡住等使用者處理——這次只定了「整批視為一個交易」的大方向，失敗時的細節行為沒有問到。
- 清單新項目「滑入＋推擠」動畫的具體方向（從左或從右）、時長、easing 曲線都還沒定案，只定了概念本身。
- 落下＋回彈的彈簧參數（阻尼、初速、超過定點的幅度）沒有定案數值，只定了動態的概念本身。
- 加密進度條需要 `LockService.EncryptAsync` 新增進度回報機制（例如 `IProgress<double>` 或類似介面），目前完全沒有這塊——這是後端新增的介面，屬於實作前要先設計清楚的範圍，不是這輪 UI 決策能定案的細節。
- 批次加密（一疊信封）情境下，「彈出＋回彈＋打開」「進度條」這幾個階段疊在一起時視覺上怎麼呈現（例如只有最上面那個信封打開顯示表單，還是每個都要各自走一次開場動畫）——這次只定案單一檔案的完整流程，批次情境下這幾個新增階段還沒有一併確認過。

### 7.2 資料夾防護（金庫門）

- 全站 `prefers-reduced-motion` 的全面盤點與補強——這輪只在新增的金庫門動畫做了範圍內處理，App.vue 既有的 modal／`table-row-in` 等動畫都還沒有這層保護。
- 批次「全部解鎖」的錯開時長／間隔（80-120ms）目前只是概念上的數值，實際串接進 App.vue、在真實列表寬高與筆數下要重新走查確認節奏是否合適，不能只憑數字複製就假設正確。
- 金庫門開／關動畫的精確 CSS 時序常數沿用 `10-vault-door.html`／《GUI造型探索_技術規格.md》既有驗證過的數值，移植進 Vue 元件（含懸浮金庫層的新情境）時要重新截圖走查一次視覺結果，不能假設原本表格列情境驗證過的手感直接套用到全螢幕懸浮層也一樣好看。

### 7.3 側欄與票根清單

- **視窗控制鈕風格切換**：新增一個設定，讓關閉／最小化／最大化按鈕可以在 macOS 造型（圓點、左上角、關閉/最小化/最大化順序）跟 Windows 造型（方形圖示按鈕、右上角、通常是最小化/最大化/關閉順序）之間切換。兩種風格都還是用 Vue 做（`.traffic-light` 這組元件本身），不是換成原生系統控制項，只是位置跟造型換一套。這輪 mockup 固定用 macOS 造型，沒有做切換功能，`13-sidebar-ticket-shell.html` 裡也用程式碼註解記錄了同樣的內容。
- **檔案類型辨識邏輯**：這輪每一列的圖示、識別色都是寫死在 mockup 裡的範例資料，正式串接時要依實際檔案（副檔名／MIME type／是不是資料夾）判斷出檔案類型。
- **圖示比對邏輯**：判斷出類型之後，要有一份「類型 → 圖示／識別色」的對照表，不是每個類型各自散落寫在畫面裡；也要決定「無法辨識/不支援的類型」要顯示哪一種預設圖示——這輪 mockup 沒有這個 fallback。
- 收合側欄的收合斷點（視窗多窄以下要不要自動收合）、hover 提示的完整互動細節，這輪都沒有問過，只做了「按鈕手動觸發收合」這一種操作方式。

### 7.4 密碼庫筆記本方向

- 這份 mockup（連同接進側欄殼子的整合版）目前／預計仍是純靜態展示搭配基本的分頁/深淺色切換，沒有接任何真正的搜尋、排序、TOTP 動態更新、密碼顯示隱藏的即時邏輯——實際串接 Vue 元件時才會補上。
- 標籤選中/未選中目前只有 CSS 兩種狀態展示，沒有點擊切換分類的完整互動。
- CSV 匯入匯出、部件管理等設定頁內部的具體表單排版還沒有實際畫出來，只定案了「這些內容跳出筆記本畫布、走中性風格頁面」這個大方向。
- 容器縮小時內部 px 數字沒有等比跟著縮小的問題，還沒有解法，下一輪如果要支援更窄的視窗寬度需要先解決（技術細節見《GUI造型探索_技術規格.md》）。

### 7.5 信封加密流程接入側欄殼子

- 信封素材的深色版本（比照 `Notebook_Body_Drack.svg` 那樣另外匯出一套）——下一輪如果要讓深色模式下信封也跟著變深，需要先請使用者出新素材。
- 步驟二表單最終是塞進信封輪廓內、還是改用 `.sheet`，實作時量測排版後要回頭把結論**寫回本節**，不要讓「各自判斷」這個開放式決策停留在「還沒決定」的狀態太久。

### 7.6 獨立解密流程（信封＋Sheet）

- `LockService.EncryptAsync`／對應解密流程需要新增一個唯讀 metadata 的介面（不執行實際解密、不需要密碼），這是後端新增的介面，實作前要先設計清楚，不是這輪 UI 決策能定案的細節。
- 清單解密拿掉「詢問存到哪裡」之後，既有的 `decryptDestination` 相關 IPC（`pickFolder` purpose、`pathPicked`／`pathPickCancelled` 分支）有一部分會變成獨立信封流程專用，需要在實作時重新梳理哪些程式碼路徑要保留、哪些要改名／收斂，避免兩套解密路徑共用同一個 purpose 字串造成混淆。
- History 表格要新增「開啟檔案位置」欄位／按鈕，需要確認 `historyItems` 現有資料結構有沒有帶著可以直接用的路徑欄位（解密的還原位置、加密的指標檔位置），如果沒有要回頭補後端資料。
