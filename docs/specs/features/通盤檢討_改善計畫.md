## 1. 第 1 輪：收斂加密流程的雙軌狀態，並修正側欄命名（已完成）

### 1.1 問題現況

**加密流程同時存在新舊兩條路徑。**

- **舊路徑**：前端送 `encrypt` 訊息，後端 `HandleEncryptRequestAsync` 一次完成加密、寫入指標檔、刪除原始檔並回報結果。前端搭配 `isEncrypting`／`encryptItemResults`／`startFakeProgress` 一組狀態，其中 `startFakeProgress` 依檔案大小估算動畫時間，逼近 92% 後停住等待，不是真實進度。
- **新路徑（信封流程）**：前端送 `encryptPending`，後端只將密文寫入 Vault、不動原始檔，前端播放信封動畫並等待使用者確認，再送 `commitEncrypt` 才真正落地。此路徑由後端推送 `encryptProgress`，數值來自 `ChunkedCipher` 實際處理的位元組數，是真實進度。

目前的實際狀態：

| 項目 | 位置 | 狀態 |
|---|---|---|
| `submitEncrypt()` | `App.vue:2077` | 已無任何呼叫端（樣板與程式碼皆無），死碼 |
| `startFakeProgress()` 及其相關狀態 | `App.vue:541` | 僅被 `submitEncrypt` 呼叫，隨之成為死碼 |
| `sendMessage` 送出 `encrypt` | `App.vue:1779`、`App.vue:2180` | **仍在使用**——巢狀資料夾防護解鎖後的加密重試 |
| 後端 `case "encrypt"` | `MainWindow.xaml.cs:343` | 仍被上述重試路徑使用 |
| 後端 `case "decrypt"` 與 `HandleDecryptRequestAsync` | `MainWindow.xaml.cs:359`、`709` | 前端無任何送出點，死碼 |
| `SIDEBAR_KEY_BY_TAB` 的 `decrypt` 鍵 | `App.vue:170` | 對應的 `activeTab === 'decrypt'` 畫面已不存在，死碼 |

使用者可觀察到的症狀：一般加密有信封動畫與真實進度條；但當加密目標內含正在防護中的資料夾、經解鎖後自動重試時，因走的是舊路徑，過程與完成皆無任何視覺回饋。此落差已記載於 `App.vue:365-371` 的註解，屬已知但未處理的範圍縮小。

**側欄命名與實際行為不符。** 側欄四個項目為「加密／資料夾防護／密碼庫／設定」，是一個動詞搭配三個名詞；且點選「加密」實際導向的是已加密清單（`App.vue:174-180` 的 `onSidebarNavigate` 將 `encrypt` 鍵映射到 `activeTab = 'list'`），與名稱暗示的動作不符。

### 1.2 根因

信封流程（Phase 2b）導入時採取範圍縮小策略，新舊兩套狀態分開以避免互相污染，但舊路徑未在新路徑穩定後移除，遺留一個未遷移的邊角案例。側欄則是在頂部水平分頁列改為側欄時，沿用了原本分頁的 `tab.*` 翻譯 key，未重新檢視「分頁標籤」與「導覽項目」在命名慣例上的差異。

### 1.3 預定改法

1. **巢狀防護重試改走信封流程**：`App.vue:1779` 與 `App.vue:2180` 兩處改為進入 `submitEncryptPending()` 的同一條路徑，使加密只剩單一實作。重試時需保留原本的加密參數（路徑、密碼、提示、Passkey／恢復金鑰、獨立加密模式）。
2. **刪除舊路徑**：移除 `submitEncrypt()`、`startFakeProgress()` 及僅供其使用的狀態（`isEncrypting`、`encryptItemResults`、假進度相關 ref）、後端 `case "encrypt"` 與 `HandleEncryptRequestAsync`。
3. **刪除已確認的死碼**：後端 `case "decrypt"` 與 `HandleDecryptRequestAsync`；`SIDEBAR_KEY_BY_TAB` 的 `decrypt` 鍵。
4. **側欄改名**：「加密」改為「檔案加密」，使四個導覽項目統一為名詞、且與「資料夾防護」形成對照，一眼可辨識本工具的兩種保護機制。需同時更新 `zh-TW.json` 與 `en.json`；新增獨立的翻譯 key（例如 `nav.fileEncryption`），不沿用 `tab.encrypt`——後者仍用於畫面內指向加密動作的按鈕文字，兩者語意已分歧。

### 1.4 不納入本輪的項目

後端 `case "restartApp"` 保留。此訊息由密碼庫共用元件 `@lx-kvn/password-locker-ui` 的 `PasswordLockerPage.vue` 送出（部件安裝完成後重啟生效），FileLocker 這個 repo 的前端搜尋不到送出點，但它並非死碼。同一個套件送出的 `openReleasesPage` 亦同。

### 1.5 驗收標準

- 全專案僅存一條加密路徑；搜尋前端送出 `encrypt` 訊息的程式碼應無結果。
- 巢狀防護解鎖後的重試會播放信封動畫並顯示真實進度。
- 側欄四個項目皆為名詞，點選「檔案加密」導向已加密清單不再構成語意矛盾。
- `dotnet test` 與 `npm run test` 全數通過。

## 2. 第 2 輪：`.flocked` 檔案自足化與 `.lockfolder` 驗證（已完成）

### 2.1 問題現況

**`.flocked` 檔案宣稱獨立可攜，實際上不是。**

前端文案（`encrypt.standaloneModeHint`）描述為「獨立可攜的 `.flocked` 密文檔」，英文版為 "self-contained, portable .flocked file"；風險提示（`encrypt.standaloneModeRiskWarning`）則說明「`.flocked` 檔案本身就是唯一副本，一旦遺失、損毀或被誤刪，內容就永久遺失，沒有辦法從集中管理區找回來」。

實際實作中（`LockService.DecryptFlockedFileCore`，`LockService.cs:722-731`），解密仍需向 Vault 讀取 `{uuid}.meta.json` 取得鹽值、Argon2 參數與密碼驗證雜湊；`.flocked` 檔頭（`FlockedFileFormat`）僅記錄 16 bytes 的 UUID 與 8 bytes 保留欄位。因此：

- 將 `.flocked` 複製到其他裝置或交付他人，無法解密。
- Vault 遺失、重建或路徑變更後，所有既存 `.flocked` 檔案永久無法解密。此風險方向未在任何 UI 文案中告知，現有風險提示只涵蓋相反方向。

**`.lockfolder` 標記檔無任何驗證。**

`FolderGuardUnlockMarkerFile.ReadTargetFolderPath` 讀出純文字內容後直接作為資料夾路徑使用，無簽章、無格式驗證、無與防護索引的比對。相對照之下，`.locked` 指標檔具備 HMAC-SHA256 簽章並驗證 UUID 為合法 GUID 格式（`LockedMarkerFile.ReadFrom`）。兩個功能等價的標記檔採用截然不同的驗證強度，且未驗證的那一個正是通往「移除 ACL 保護」流程的入口。

### 2.2 預定改法

**`.flocked` 格式升級至 v2。** metadata 區塊放在**檔尾**，不是接在 header 之後：

```
┌─ Header（31 bytes，與 v1 相同，僅版本號改為 2）──┐
│ Magic bytes (4 bytes)          "FLKD"           │
│ 版本號 (1 byte)                 2                │
│ Header 總長度 (2 bytes, big-endian)              │
│ UUID (16 bytes)                                 │
│ 保留欄位 (8 bytes)                                │
├─ 密文（ChunkedCipher 串流）────────────────────┤
├─ 檔尾（v2 新增，commit 階段才追加）─────────────┤
│ Metadata JSON (UTF-8, N bytes)                  │
│ N (4 bytes, big-endian)                         │
│ 檔尾 magic (4 bytes)           "FLKM"            │
└────────────────────────────────────────────────┘
```

**放檔尾而非接在 header 之後，因為**寫入時機對不上：header 必須在加密開始之前就寫（密文緊接在它後面），但 Passkey／恢復金鑰的包裝金鑰是整份內容加密完成之後才產生的。放檔尾的話，commit 階段對既有的暫存密文檔直接 append 再 `File.Move` 即可，維持 O(1) 的搬移成本；若改為接在 header 之後，每次 commit 都必須把整份密文重讀重寫一次，大型項目的差異極為顯著。

此結構要求呼叫端框出密文的範圍：`ChunkedCipher.DecryptStream` 讀到串流結束為止，不框範圍會把檔尾的開頭四個位元組當成下一個區塊的長度前綴解析。新增 `Io/BoundedReadStream` 承擔此職責——不改由 `ChunkedCipher` 自行接收長度參數，因為「密文到哪裡結束」是 `.flocked` 這個容器格式的問題，而 `ChunkedCipher` 同時服務 Vault 模式（整個 `.enc` 檔案就是密文），那邊沒有這個概念。

版本號提升至 2，因為 v1 的讀取端遇到 v2 檔案會把檔尾當成密文的一部分解析，產生難以理解的「內容損毀」錯誤；提升版本號使舊版明確拒絕，而非給出誤導性的失敗。讀到版本 1 的檔案時退回既有行為（向 Vault 查詢 metadata），保持既有檔案可解密。

嵌入的 metadata 需包含：`Salt`、`Argon2TimeCost`、`Argon2MemoryCostKb`、`Argon2Parallelism`、`PasswordVerificationHash`、`OriginalName`、`Type`、`OriginalSizeBytes`、`Hint`、`PasskeyEnabled` 與相關包裝金鑰欄位、`RecoveryKeyEnabled` 與相關包裝金鑰欄位。

**`OriginalPath` 不嵌入，因為**該欄位對解密流程沒有作用（`.flocked` 的密文從使用者實際點開的檔案讀取，不從 `OriginalPath` 反推），保留它只會讓檔案攜帶使用者的資料夾結構資訊到不受控制的位置。還原目的地改用 `.flocked` 檔案所在資料夾，此行為與現有 `DecryptFlockedFileCore` 一致。

此變更使 `.flocked` 檔案攜帶密碼驗證雜湊。其曝光程度與 `meta.json` 存放於雲端同步資料夾時相同（雜湊不可逆推回密碼），但檔案的可攜性使它更容易被帶到使用者控制範圍之外，屬於為兌現「獨立可攜」承諾而接受的取捨。

**`.lockfolder` 驗證機制。** 判準為與防護索引比對：讀出的資料夾路徑必須存在於 `FolderGuardStore` 且狀態為 `Locked`，否則整筆忽略（`FolderGuardService.ResolveUnlockMarkerTargetsAsync`）。索引才是「這個資料夾現在是否在防護中」的權威來源，內容被改成指向任何不在索引中的路徑都不會有作用。

**不另外加註簽章，因為**它擋不住上述以外的情況——標記檔內容被改成指向另一個確實在防護中的資料夾時，也只是替那個資料夾跳出解鎖彈窗，解鎖本身仍然要通過密碼或 Passkey，不構成繞過；但加註簽章會使使用者磁碟上既有的標記檔全部失效，必須重新上鎖一次才能恢復雙擊解鎖功能。

### 2.3 驗收標準

- 新產生的 `.flocked` 檔案在 Vault 完全不存在的情況下（模擬換裝置）仍可解密。
- v1 格式的既有 `.flocked` 檔案維持可解密。
- 內容被改為任意路徑的 `.lockfolder` 標記檔不會觸發任何解鎖流程。
- 文案同步修正：`.flocked` 的「獨立可攜」在 v2 之後成立，並在說明中具體交代成立的範圍。

### 2.4 執行結果（2026-08-27）

**`.flocked` v2 格式**（`FlockedFileFormat`）：新增 `AppendMetadataTrailer`／`TryReadLayout` 與 `FlockedFileLayout` 記錄型別；`TryReadHeader` 改為接受版本 1 與 2（原本只接受當前版本，升版會讓既有檔案全部讀不出 UUID）。嵌入的 metadata 由 `ToPortableMetadata` 產生副本，清除 `OriginalPath` 與 `StandaloneDestinationDir`，其餘欄位原樣保留。序列化的欄位命名規則與 `VaultManager` 寫 `.meta.json` 時一致，兩邊可互相讀回；差別僅在不縮排，以節省每顆 `.flocked` 檔案的體積。JSON 長度設 1 MB 上限，用意與 `ChunkedCipher.MaxChunkLengthBytes` 相同。

**寫入時機**：`CommitStandaloneEncryptAsync` 在 `File.Move` 之前以 append 方式補上檔尾，並排在 `Status = Committed` 賦值之後，使嵌入的那份帶著最終狀態而非 `Pending`。

**metadata 來源的優先順序**：`LockService.ResolveMetadataForDecrypt` 統一處理——Vault 查得到就以 Vault 那份為準，查不到才讀檔尾。順序不可對調：同一台裝置上使用者可能事後重新設定過該項目的 Passkey，那種變更只反映在 Vault 的 `.meta.json` 上，檔尾那份是加密當下固定寫死的。檔尾那份的定位是「Vault 不在了」時的後備。

**`.flocked` 路徑在解密流程中的傳遞**：`PendingDecrypt` 記錄型別新增 `FlockedPath` 欄位；`TryLoadMetadata`／`ResolveDestinationParentDir`／`FinishAfterKeyResolved`／`CleanupOriginalArtifactIfMatches` 及三個 `VerifyDecrypt*`／三個 `DecryptBy*` 入口皆新增選填的 `flockedPath` 參數。前端在 `inspectLockedFile` 之後把選中的 `.flocked` 路徑記進 `decryptItemInfo`，三個 verify 請求一併送出，經 `MainWindow.ReadFlockedPath` 取出後往下傳。

`ResolveDestinationParentDir` 另外處理一個直接後果：檔尾的 metadata 不帶原始路徑，使用者未指定還原位置時改用 `.flocked` 檔案目前所在的資料夾——這也才符合「搬到哪就在哪還原」的可攜語意。`CleanupFlockedIfMatches` 同理，優先使用呼叫端手上實際的路徑，不用 `OriginalPath` 反推。

**新增的路徑式入口**：`DecryptFlockedFileByRecoveryKeyAsync`／`DecryptFlockedFileByPasskeyAsync`。需要以「檔案路徑」為起點的入口，是因為 Vault 不在時呼叫端手上只有這顆檔案，沒有紀錄可以先查出 UUID。Passkey 之所以也提供，是為了涵蓋「同一台裝置、但 Vault 遺失或重建」——憑證仍在本機 TPM 內、包裝過的內容金鑰在檔尾，兩者湊齊即可解開。`PasswordPromptWindow`（雙擊 `.flocked`）的恢復金鑰與 Passkey 路徑改為呼叫這兩個入口，並在 Vault 查不到 metadata 時退回讀檔尾以顯示檔名、提示與可用的解鎖方式；`VaultProtocolHandlers.InspectLockedFile` 同樣加上此後備。

**CLI 同步**：`unlock-recovery` 的第一個參數改為接受 uuid 或 `.flocked` 路徑（傳路徑時從檔頭讀出真正的 uuid，JSON 輸出的 `uuid` 欄位仍是 uuid 而非路徑），對應 GUI 端雙擊 `.flocked` 改用恢復金鑰解鎖的同一條路。使用說明的中英文皆已更新。

**`.lockfolder` 驗證**：`FolderGuardService.ResolveUnlockMarkerTargetsAsync` 依上述判準過濾；`App.xaml.cs` 的 `HandleFolderGuardUnlockMarkerLaunch` 改為呼叫它，並在一筆都通不過時呼叫 `ShutdownIfNoWindowsRemain`——這個行程是被雙擊觸發起來的，沒有視窗會開就必須結束，不能留下看不見也殺不掉的行程（比照 `--startup` 分支的既有處理）。回傳的是索引裡那份路徑而非標記檔寫的那份，避免大小寫與尾端分隔符差異造成後續比對落差。

驗證結果：`dotnet test` 通過 375 個（Core 305、Cli 62、App 8），失敗 0；新增 20 個測試（`.flocked` v2 格式 8、`BoundedReadStream` 6、`.lockfolder` 驗證 6），另在 `LockServiceTests` 新增 6 個可攜性整合測試（無 Vault 紀錄仍可解密、密碼錯誤仍照擋、資料夾型別正確還原、恢復金鑰可用、搬移後在原地還原、Vault 存在時以 Vault 為準）。`npm run test` 通過 121 個；四個專案建置皆無警告無錯誤。

## 3. 第 3 輪：保護等級一致化

### 3.1 問題現況

**關鍵操作驗證的覆蓋範圍與動作的不可逆程度不成比例。**

| 動作 | 後果 | 目前的驗證要求 |
|---|---|---|
| 清除使用紀錄 | 僅刪除本機操作日誌，加密內容不受影響 | 強制。未設定過關鍵操作驗證則整個功能無法使用，且流程為三步驟（確認→Windows Hello→最終確認） |
| 永久刪除加密項目 | 加密內容真正消失，無法復原 | 僅需重新輸入該項目密碼 |
| 搬移 Vault 位置 | 可逆 | 條件式（已設定過才驗證） |

三個動作採用三種不同規則，且保護最重的是後果最輕的動作。

**資料夾防護的密碼鎖定機制與其自身的復原路徑互相抵消。** `FolderGuardService` 套用與加密相同的 `LockoutTracker`（連續錯誤 5 次後指數退避，上限 3600 秒），鍵值為固定常數 `folder-guard-unlock`，鎖定範圍涵蓋所有防護中的資料夾。同時，規格第 21.1 節記載忘記密碼時可透過檔案總管「內容→安全性→進階」自行取回存取權，且設定頁主動告知此事。因此鎖定期間內，任何知悉該途徑的人可立即繞過，鎖定實際上只影響輸入錯誤的合法使用者。

**四套憑證系統外觀相同但後果不同。** 目前並存的憑證系統為：每個加密項目各自的密碼（＋選配 Passkey／恢復金鑰）、資料夾防護的共用密碼（＋選配 Passkey）、關鍵操作驗證的 Windows Hello 憑證、密碼庫主密碼（位於 PasswordVault repo）。其中三套在 UI 上均稱為「密碼」、三套均可搭配 Passkey，但遺失後的結果差異極大——加密項目密碼遺失即永久無法復原，資料夾防護密碼遺失可自行取回。此差異目前未在任何 UI 文案中呈現。

### 3.2 預定改法

**建立四層保護等級，依「後果的不可逆程度」而非「動作名稱的嚴重感」分層：**

| 層級 | 判準 | 驗證要求 | 適用動作 |
|---|---|---|---|
| T0 | 完全可逆、無資料損失 | 無 | 切換語言／主題／視窗造型、展開清單、前往資料夾、查看說明 |
| T1 | 取回自己的內容 | 一次身分證明（項目密碼／Passkey／恢復金鑰） | 解密、資料夾解鎖 |
| T2 | 影響範圍大但可復原 | 密碼＋明確確認 | 搬移 Vault、停用資料夾防護、停用 Passkey、清除使用紀錄 |
| T3 | 內容永久消失 | 密碼＋關鍵操作驗證＋最終確認 | 永久刪除加密項目 |

實際調整兩項：

1. **永久刪除加密項目提升至 T3**：這是本工具中唯一一個執行後內容真正無法復原的動作，現行僅要求密碼。
2. **清除使用紀錄下降至 T2**：保留關鍵操作驗證（該動作仍有隱私意義——日誌記載使用者操作過哪些檔案），但將「未設定過即整個功能停用」改為「未設定過則退回一般確認彈窗」，與搬移 Vault 的條件式行為一致。

調整後規則可收斂為單一句子：**已設定過關鍵操作驗證時，T2 以上一律要求驗證；未設定過則退回確認彈窗，但 T3 必定要求密碼。** 三個動作三種特例的狀態隨之消除。

**資料夾防護鎖定機制調整。** 退避上限由 3600 秒降至 60 秒（公式改為 `min(5 × 2^n, 60)`），門檻維持連續錯誤 5 次。此調整將機制目的由「拖慢持續嘗試的攻擊者」改為「阻擋連續誤觸」，理由是該功能的威脅模型為「同一台裝置上的其他人隨手嘗試」，60 秒足以使該對象放棄或使擁有者察覺；而合法使用者輸入錯誤時的等待成本大幅降低，不會被工具本身阻擋在外。

同時將「可透過檔案總管取回存取權」的說明由設定頁常駐文案移至說明彈窗，並在連續解鎖失敗時才主動提示。此途徑為必要的復原手段（資料夾防護沒有恢復金鑰可兜底），但不需要在使用者尚未遇到問題時即主動公告。

**憑證命名區隔。**

| 現行稱呼 | 改為 | 遺失後果 |
|---|---|---|
| 密碼（每個加密項目各自一組） | 項目密碼 | 永久無法復原，無後門機制 |
| 密碼（資料夾防護共用一組） | 防護密碼 | 可透過 Windows 權限自行取回 |
| 關鍵操作驗證（Windows Hello，無密碼） | 維持原名 | 可重新設定 |
| 密碼庫主密碼（PasswordVault repo） | 密碼庫主密碼 | 依該 repo 的設計 |

每一個設定憑證的畫面固定加入一行說明遺失後的結果，並於說明彈窗新增一張四套憑證的對照表。此差異是四套系統之間最具實質意義的區別，卻是目前唯一未呈現的資訊。

### 3.3 驗收標準

- 永久刪除加密項目在已設定關鍵操作驗證時會要求 Windows Hello。
- 清除使用紀錄在未設定關鍵操作驗證時仍可執行（經確認彈窗）。
- 資料夾防護連續錯誤後的最長鎖定時間為 60 秒。
- 四套憑證在 UI 上使用各自的專屬名詞，且各自的設定畫面均載明遺失後果。

## 4. 第 4 輪：進度回報一致化

### 4.1 問題現況

三處對「是否有真實進度回報」的敘述互相矛盾：

- `ChunkedCipher.cs:61` 確實呼叫 `progress.Report(...)`，依實際處理的位元組數計算。
- `MainWindow.HandleEncryptPendingRequestAsync`（`MainWindow.xaml.cs:653`）確實建立 `Progress<double>` 並推送 `encryptProgress` 給前端。
- `FileLocker.Cli/Program.cs:57-62` 的註解與技術規格文件第 24.2 節仍記載「全專案（含 GUI）從來沒有任何地方真的呼叫過 `.Report(...)`」，並據此決定 CLI 只顯示忙碌旋轉指示器而不顯示百分比。

該前提在信封流程導入後已不成立，但依據該前提做出的決定仍然保留。此外，解密路徑的 `ChunkedCipher.DecryptStream` 沒有 `IProgress<double>` 參數，因此加密有真實進度、解密完全沒有。

### 4.2 預定改法

1. `ChunkedCipher.DecryptStream` 新增 `IProgress<double>?` 與 `totalBytes` 參數，比照 `EncryptStream` 的既有做法回報進度。
2. `LockService` 的解密路徑將 progress 參數往下傳遞；`VaultProtocolHandlers` 與 `MainWindow` 對應的解密處理接上，推送給前端。
3. CLI 的 `encrypt` 與 `unlock` 改為顯示真實百分比，取代 `WithSpinnerAsync` 的忙碌指示器。在 `--output json` 或輸出被重新導向時維持關閉，此既有行為不變。
4. 移除 `Program.cs` 與技術規格文件中「從來沒有任何地方真的呼叫過」的過期敘述。

### 4.3 驗收標準

- CLI 執行 `encrypt` 與 `unlock` 時顯示與實際處理量對應的百分比。
- GUI 解密流程顯示真實進度。
- 專案內不再有敘述 `IProgress` 為未使用參數的註解或文件段落。

## 6. 已知限制

- **改版前產生的 v1 `.flocked` 檔案無法回溯補上驗證材料**：那些檔案的檔尾沒有 metadata 區塊，仍然只能靠 Vault 解密，換裝置或 Vault 遺失後即無法開啟。要補上必須改寫既有檔案本身（不只是追加，還得同步更新版本號欄位），屬於會動到使用者現有資料的操作，本次不執行。受影響的使用者可將檔案解密後重新以獨立加密模式加密一次，產生的即為 v2 格式。
- **`.flocked` v2 使檔案攜帶密碼驗證雜湊**：這是兌現「獨立可攜」承諾的必要條件——沒有驗證材料就無法在缺少 Vault 的環境判斷密碼是否正確。雜湊本身不可逆推回密碼，曝光程度與 `meta.json` 存放於雲端同步資料夾時相同，但檔案的可攜性使它更容易離開使用者的控制範圍。
- **資料夾防護的鎖定機制無法阻擋知悉 ACL 途徑的對象**：這是該功能定位（防隨手瀏覽，非防蓄意繞過）的必然結果，見 ADR-0001。第 3 輪的調整是讓機制的強度與其實際能達成的目的一致，不是提升防護能力。
- **`vault.config.json` 的 ACL 硬化在雲端同步情境下不成立**：該檔案以 Windows ACL 限制為僅目前使用者可存取，但 Vault 的設計同時鼓勵將其指向雲端同步資料夾供多台裝置共用，兩者的目的互相抵消。本次檢討未安排處理輪次，僅記錄於此。
