# FileLocker GUI 造型探索——資料夾防護「金庫門」定案

## 背景

金庫門（保險箱／轉輪＋門扇）的造型比喻最早是在《信封蠟封方向定案文件》裡，跟信封那套一起
定案的——當時只確認了圖層結構跟清單列常態的互動細節，「完整開門動畫（框架＋門扇＋轉輪整套）
究竟在使用者操作的哪個時間點出現」這件事其實從未真正定案過，舊文件的〈金庫門分頁的互動細節〉
只寫了轉輪單獨旋轉的部分，沒有指定門扇何時打開。

這份文件把資料夾防護專屬的金庫門決策獨立出來，原因有二：一是金庫門跟信封是兩套完全獨立的
造型語言（服務不同分頁、不同操作性質），混在同一份文件裡，之後回頭找資料夾防護的細節要在
信封敘事裡大海撈針；二是這輪 grilling 補上的「新增資料夾的開門儀式」是一段舊文件完全沒有
處理過的新流程，適合單獨立文件記錄，不是舊決策的修訂。

《信封蠟封方向定案文件》原本的〈金庫門動畫的圖層結構〉〈金庫門分頁的互動細節〉兩節（含決策
記錄表）已整段移入本文件下方，該份文件保留指向本文件的備註，避免同一份決策存在兩個地方。

## 金庫門動畫的圖層結構

資料夾防護頁的金庫門，最後決定不走跟信封同等複雜度的「轉盤／把手／門閂各自獨立」四拍模擬，
改成參考常見的金庫圖示慣例——用**一個帶輻條的大轉輪同時代表轉盤跟把手**（不分開畫兩個零件），
門閂也不特寫，只靠門體本身的開合傳達「鎖住/打開」。動畫收斂成兩拍：

1. **轉輪旋轉**（`rotateZ`，原地自轉，代表輸入密碼＋扳動開鎖一次做完）
2. **門扇打開**（`rotateY`，繞右側鉸鏈轉開，角度封頂在 70-80 度、不轉到會露出門背面的角度，
   `ease-in-out`，450-550ms，門扇是最後一步、份量最重）

鉸鏈定案在**右側**（門往左邊掀開），`Vault_Frame.svg` 右側已經畫出對應的鉸鏈缺口。三層各自的
職責：

- `Vault_Frame.svg`（已定案）：固定不動，外殼＋凹陷開口＋右側鉸鏈缺口＋開口邊緣內陰影
- `Vault_Door_Slab.svg`：門體本身，不含轉輪，右側要畫出鉸鏈細節對上 `Vault_Frame` 的缺口位置，
  尺寸要能剛好蓋住開口
- `Vault_Wheel.svg`：轉輪本身，疊在門體正中央，黃銅金色、細線條風格跟其他素材一致，自己原地旋轉

> 補充（技術規格已驗證，實作時直接沿用）：實際 mockup（`10-vault-door.html`）驗證下來，門扇
> 鉸鏈是**左側**（`transform-origin:21%`），跟這一段文字描述的「右側」不一致——這是舊文件本身
> 遺留、從未回頭修正的落差。以 `信封蠟封_技術規格.md` 第 3 節（含 `Vault_Frame.svg`／
> `Vault_Door_Slab.svg` 實際的鉸鏈缺口位置）為準，不要照這段文字的「右側」重新畫素材或重寫
> CSS。轉輪與門扇的精確 CSS keyframe、時序常數（`WHEEL_OPEN_MS=650`、`WHEEL_CLOSE_MS=780`、
> `DOOR_MS=500`、接力時序、「喀」一聲回彈手感）都記在同一份技術規格文件第 3 節，這裡不重複。

## 金庫門分頁的互動細節

這輪 grilling 之前先去讀了 `FileLocker_技術規格文件.md` 第 21 節「資料夾防護」的既有機制
（唯讀查證，不是猜測），確認幾個跟信封本質不同的地方，直接影響這輪的決策方向：

- 上鎖／解鎖目前分兩條路：**右鍵選單觸發的走原生 WPF 小視窗**（`FolderGuardConfirmLockWindow`／
  `FolderGuardUnlockPromptWindow`，刻意不透過 WebView2，避免為了一個右鍵確認動作啟動整個
  WebView2 環境），**只有 App 內「資料夾防護」分頁是 WebView2/Vue 畫面**。
- 分頁本身已經有「新增資料夾」按鈕，可以直接發起新的上鎖，不是只能靠右鍵選單。
- 上鎖本身**不需要密碼**、是近乎瞬間完成的 ACL 操作（不像加密要花時間寫入 Vault），解鎖才需要
  驗證身份。
- 解鎖後的資料夾**留在清單裡**（可「前往資料夾」或「再次上鎖」），不會像信封解密後那樣離開
  清單——兩者清單語意不同：信封清單記錄「加密過的檔案」，解密後不再符合這個狀態理應離開；
  資料夾防護清單記錄「持續管理中的資料夾」，上鎖或解鎖都還是同一批要繼續管理的資料夾。

### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 金庫門動畫的適用範圍 | **只用在 App 內「資料夾防護」分頁，不動右鍵選單觸發的原生 WPF 小視窗** | 那兩個原生視窗是刻意不透過 WebView2 的既有架構決策，硬套動畫等於推翻這個決策，範圍會從「畫面美化」變成「原生視窗架構改動」 |
| 分頁內新增資料夾／再次上鎖要不要額外確認彈窗 | **不需要**，選定資料夾／按下按鈕本身就是明確意圖 | 右鍵選單需要確認彈窗是為了防止滑鼠移動中誤觸；App 分頁裡「新增資料夾」要先跳系統資料夾選取器、明確選一個資料夾，這一連串操作本身已經是刻意動作，金庫門的關閉動畫本身就是最好的即時回饋，不需要再疊加一層彈窗 |
| 清單常態（沒有動畫播放時）的呈現 | **輕量化**：欄位順序**轉盤－資料夾路徑－狀態－解鎖按鈕**，不是每列都畫完整立體金庫門 | 金庫門是立體、有厚度感的物件，硬要壓扁成一列會失去重量感、也不好辨識（不像信封本來就是扁平的紙）；資料夾防護操作性質比加密輕量，清單常態也該輕量，金庫門的視覺重量感留給「動作發生當下」集中呈現 |
| 轉盤在清單列的角色 | 轉盤是**持續顯示的小圖示**（取代通用鎖頭圖示），**可以直接點擊，效果等同按下「解鎖」按鈕** | 把「金庫」的視覺識別（轉盤造型）壓縮進清單常態的輕量圖示裡，不需要額外疊加畫面 |
| 點擊轉盤（或按解鎖按鈕）的完整互動時序 | ① 點擊轉盤：**小幅轉動立刻彈回**（驗證還沒過的即時觸感回饋，只有直接點轉盤才有這一步）② 跳出密碼／Passkey 驗證 ③ 驗證成功後，**轉盤才真正完整轉一圈**——**只有轉輪動，不牽動門扇／框架** | 呼應「轉開保險箱」的物理直覺：先摸一下試試看（immediate feedback），真正打開要等驗證通過。清單列本來就只常態顯示轉輪（見上一列），解鎖動作的完整動畫延續同一個視覺元素，不無中生有帶出門扇跟框架——完整的金庫立體場景（框架＋門扇＋轉輪）保留給下方〈新增資料夾的開門儀式〉那個獨立情境 |
| 觸發方式是否影響完整轉一圈動畫要不要播 | **不影響**——不論從轉盤或「解鎖」按鈕觸發，驗證成功後完整轉一圈都會播 | 完整旋轉代表「狀態真的改變了」這個事實本身，不是點擊方式的專屬獎勵；只有「小幅回彈」前導動作才是直接點轉盤才有的額外回饋 |
| 「再次上鎖」（relock，既有已解鎖列，不需要密碼）要不要播動畫 | **要**，播一段**反方向**的完整轉輪旋轉，點下去立刻播（不用等後端回應——後端本來就是 fire-and-forget，沒有可以等待的結果） | 跟解鎖的正向完整旋轉做出方向上的區隔，讓「解鎖」跟「上鎖」兩個語意相反的動作不會共用同一種「轉一圈」觀感而分不清楚剛剛發生了什麼；不需要密碼，也就沒有「先小幅回彈等驗證」這個前導階段，直接播完整動畫 |
| 「解鎖全部」時，多個轉盤怎麼一起播放解鎖動畫 | **依序錯開**（由上到下，間隔 80-120ms 開始轉），不是全部同時轉。後端 `FolderGuardService.UnlockAllAsync` 目前只回傳單一聚合結果，沒有逐筆進度事件（探索階段已查證），這個錯開效果**這輪只做前端假的**：觸發批次解鎖前先記住當下所有「已鎖定」的路徑清單，後端回傳整批成功後，前端自己用 `setTimeout` 依序播放清單裡這些列各自的完整轉動，全部播完才真正重新整理列表 | 多個轉盤同時動作視覺上是一團混亂的旋轉；依序錯開的小延遲讓眼睛自然跟著節奏往下看，畫面更有秩序，也呼應金庫門這種帶儀式感的操作。不改後端是這輪明確的範圍決定（見〈範圍決策〉）——真正的逐筆後端事件屬於未來如果要做「即時反映哪一筆卡住／失敗」才需要的東西，這輪批次操作本身就是全有全無，沒有這個需求 |
| 轉輪停到定位時要不要有「喀」一聲卡住的回彈手感 | **要**：轉盤用先加速、持續減速、到定位前衝過頭一點點再彈回卡住的動態，不是線性轉到底就停 | 呼應「漸漸變慢＋最後頓一下」的物理直覺；用 CSS `@keyframes` 分段控制速度曲線達成，細節（含調參數時踩過的坑）記在《信封蠟封_技術規格.md》 |
| 轉輪最終停等角度 | 必須是 **90° 的整數倍** | 轉盤本體是四個握把、四等分的造型，停在任意角度會讓握把跟門框/外殼的相對位置歪掉、視覺上不對稱；90° 的倍數保證每次停下來造型都是正的 |
| 開鎖／上鎖兩個方向的轉輪速度曲線要不要一樣 | **不用完全一樣，但收尾都要乾脆俐落**——共用同一條收尾曲線形狀，靠時長跟轉的圈數區分兩個方向的手感，不是靠曲線形狀本身區分 | 開鎖是「解開束縛」、上鎖是「扣上收尾」，語意不同，時長跟圈數的差異已經足夠讓兩者播起來能感覺出差異；曲線形狀本身反而是收尾「乾不乾脆」的關鍵 |
| 解鎖後資料夾要不要離開清單 | **留在清單裡**，維持既有行為（可再次上鎖或前往資料夾） | 資料夾防護清單記錄的是持續管理中的資料夾，跟信封「已加密清單」的語意不同，不能套用信封那套「解密後離開清單」的邏輯 |

## 清單常態圖示的狀態區分（這輪新定案）

清單列常態顯示的轉輪圖示（見上表「清單常態的呈現」「轉盤在清單列的角色」），已鎖定跟已解鎖
兩種狀態用**同一套顏色（`--tint-guard` 系列既有 token，不新增顏色 token），靠轉輪角度／
透明度做區分**，不做成兩種色階。理由：資料夾防護清單本來就已經有純文字的狀態欄位
（`folderGuard.statusLocked`／`statusUnlocked`）並存，轉輪圖示的角色是「可點擊的視覺化鎖頭」，
不是唯一的狀態指示來源，不需要為了圖示本身再疊加一組新的顏色語言；同一套金色（`#A8770F`
系列，跟信封蠟封敘事的呼應色一致）維持整個資料夾防護頁面的色彩一致性。

## 新增資料夾的開門儀式（這輪新定案）

這是舊文件從未定案過的空白——〈金庫門分頁的互動細節〉只講了「轉輪單獨旋轉」用在解鎖／
上鎖，完整的立體金庫場景（框架＋門扇＋轉輪）究竟何時出現，之前沒有問到。這輪確認：**完整
開門／關門動畫只用在「新增資料夾」這個流程**，不是解鎖既有項目的一部分。

完整流程：

1. 使用者按下「新增資料夾」按鈕。
2. 畫面疊一層**全螢幕懸浮金庫層**，背景加模糊（`backdrop-filter: blur()`），呈現一座**關閉
   狀態**的完整金庫（框架＋門扇＋轉輪）。
3. 播放開門動畫（轉輪旋轉→門扇打開，接力時序，沿用〈金庫門動畫的圖層結構〉既有的 CSS
   時序常數）。
4. **門完全打開之後**，才彈出 Windows 原生「選擇資料夾」對話框。
5. 使用者選定資料夾，或按取消。
6. 不論選定或取消，都播放**完整的關門動畫**（門扇關上→轉輪轉回去，接力反向）。
7. 關門動畫播完，懸浮金庫層才消失。
8. 若使用者確實選定了資料夾：**不需要密碼、立即自動保護**，該資料夾馬上以「已鎖定」狀態出現
   在清單裡——沿用《信封蠟封方向定案文件》原本就定案的「新列進場：滑入＋推擠，轉盤同時反方向
   旋轉、阻力遞增、最後卡進定位有頓挫感」那套既有動畫（見上方移入的決策記錄表），這裡不是
   重新設計一套新的進場方式，是接續在懸浮金庫層消失之後發生的下一段。

### 決策記錄

| 決策點 | 結論 | 理由 |
|---|---|---|
| 開門動畫跟 Windows 選資料夾視窗的時序關係 | **門開完才彈選資料夾視窗** | 因果關係最直白——「開了金庫門才能進去選東西」，動畫語意跟操作順序一致 |
| 選定／取消後金庫怎麼收場 | **播完整關門動畫才消失**，選定跟取消走同一套收場方式，不因結果不同而有差異視覺 | 開跟關要對稱，才不會「開門很隆重、關門悄悄消失」這種頭重腳輕的觀感；取消不代表操作異常，不需要額外的錯誤/警告視覺 |
| 新增後要不要額外確認才正式保護 | **不需要，選完就自動保護、立刻顯示已鎖定** | 對應資料夾防護「上鎖不需要密碼、近乎瞬間完成」的既有性質；選擇資料夾這個動作本身已經是明確意圖，疊加一層確認彈窗只是重複詢問 |
| 懸浮金庫層的呈現方式 | **背景模糊＋全螢幕疊層**，不是塞進表格某一格或讓某一列的高度撐開 | 這是全新的「新增」動作，跟清單裡任何一個既有項目都無關，不該從某一列的位置長出來；背景模糊讓場景維持 mockup 驗證過的原始比例（320×280 或更大），不需要為了塞進小空間重新設計縮小版素材 |

## 素材遷移方式（這輪新定案）

`Vault_Wheel.svg`／`Vault_Door_Slab.svg`／`Vault_Frame.svg` 目前只存在於repo 根目錄的
`assets/` 資料夾，`src/FileLocker.Web/src/assets/` 裡還沒有。這輪決定**直接複製原始檔案**
過去，不重新設計或匯出縮小尺寸的版本——mockup（`10-vault-door.html`）已經驗證過的比例、
線條粗細直接沿用，懸浮金庫層本身就是全螢幕疊層，不受限於清單欄位的小尺寸，沒有另外做一套
「小尺寸專用素材」的必要。

## 減少動畫（`prefers-reduced-motion`）處理範圍（這輪新定案）

目前整個 `FileLocker.Web` 專案**沒有**處理 `prefers-reduced-motion` 這個使用者偏好設定的
既有機制（探索階段已查證，非猜測）。這輪範圍限定：**只在這次新增的金庫門相關 CSS 動畫**加上
`@media (prefers-reduced-motion: reduce)` 保護——轉輪旋轉、開門／關門動畫，在這個偏好開啟時
全部改成一段短暫的淡入淡出（`opacity`，約 150-200ms），不做旋轉或位移；Windows 原生「選擇
資料夾」對話框本身不受影響，維持系統原生行為。

App.vue 裡既有的其他動畫（modal 淡入淡出、`table-row-in` 清單進場等）這輪**不**一併補上
`prefers-reduced-motion` 保護，列入下方待辦事項，之後要對全站動畫做一次盤點時再一起處理，
不在這輪金庫門範圍內。

## 文件歸屬

這份文件獨立於《信封蠟封方向定案文件》之外——金庫門跟信封是服務不同分頁、不同操作性質的
兩套造型語言，混在同一份文件裡不利於之後查找。原本在信封文件裡的〈金庫門動畫的圖層結構〉
〈金庫門分頁的互動細節〉兩節（含決策記錄表）已整段移入本文件，信封文件保留一個指向本文件
的備註，避免同一份決策同時存在兩個地方、日後修改時漏改其中一份。

## 已知限制

- 「解鎖全部」的錯開動畫是前端自己模擬（記住觸發前的鎖定清單，成功後用 `setTimeout` 依序
  播放），後端沒有真正的逐筆進度事件——如果某一筆解鎖實際上失敗（目前後端是整批全有全無，
  理論上不會發生單筆失敗），前端播放的錯開動畫仍然是「假設全部都成功」的樂觀呈現，不會反映
  真實的逐筆狀態。
- 懸浮金庫層的背景模糊（`backdrop-filter`）在極舊版 WebView2/Chromium 核心下可能不支援或
  效能不佳，這輪沒有另外規劃降級方案（沒有測試環境驗證這個風險是否存在）。

## 待辦事項

- 全站 `prefers-reduced-motion` 的全面盤點與補強——這輪只在新增的金庫門動畫做了範圍內處理，
  App.vue 既有的 modal／`table-row-in` 等動畫都還沒有這層保護。
- 批次「全部解鎖」的錯開時長／間隔（80-120ms）目前只是概念上的數值，實際串接進 App.vue、在
  真實列表寬高與筆數下要重新走查確認節奏是否合適，不能只憑數字複製就假設正確。
- 金庫門開／關動畫的精確 CSS 時序常數沿用 `10-vault-door.html`／《信封蠟封_技術規格.md》
  第 3 節既有驗證過的數值，移植進 Vue 元件（含懸浮金庫層的新情境）時要重新截圖走查一次視覺
  結果，不能假設原本表格列情境驗證過的手感直接套用到全螢幕懸浮層也一樣好看。
