# 密碼庫瀏覽器整合採用正式擴充功能＋Native Messaging，不用 Tampermonkey 使用者腳本＋本機伺服器

**狀態**：accepted

密碼庫（Password Locker）需要瀏覽器端能偵測登入表單、跟本機常駐程式要密碼填入，這需要瀏覽器跟本機程式之間有一條通道。考慮過兩個方案：

1. **正式擴充功能＋ Native Messaging**（採用）：寫一個正式的瀏覽器擴充功能，上架 Chrome 線上應用程式商店（一次性 5 美元開發者註冊費，可透過 CI 自動上傳，但實際審核時間不可控，可能數小時到數天）。瀏覽器跟本機常駐程式之間走瀏覽器原生的 Native Messaging API，連線對象在作業系統層級鎖死——只有登記在常駐程式 manifest 的 `allowed_origins` 裡的擴充功能 ID 能連上，其他網頁的 JS 完全碰不到。
2. **Tampermonkey 使用者腳本＋本機 HTTP 伺服器**：不上架任何擴充功能，改發布一個 `.user.js` 使用者腳本（放在自己的 GitHub Release，Tampermonkey 內建 `@updateURL` 自動更新），使用者透過已經裝好的 Tampermonkey 執行。免商店審核、免開發者費用。但使用者腳本沒有 Native Messaging 權限，常駐程式必須改成在 `127.0.0.1` 開一個本機 HTTP／WebSocket 伺服器，使用者腳本改用一般 `fetch` 呼叫。這個伺服器原則上任何網頁的 JS 都打得到（不只是我們自己的腳本），是市面上其他「本機伺服器橋接」類密碼工具實際出過 CVE 的攻擊面（惡意網頁跨源打本機伺服器騙出密碼），要守住至少需要：只有腳本自己拿得到的秘密 token（不能放在網頁可讀的 `localStorage`）、嚴格檢查請求來源——這是需要額外設計、測試的安全機制，不是裝了就沒事。

選擇方案 1：密碼庫存放的是使用者所有網站的帳密，是這個功能裡風險最高的攻擊面，Native Messaging 在作業系統層級把「誰能連線」鎖死是廠商已經幫忙做好、經過大規模驗證的安全邊界；方案 2 省下的錢與審核等待時間，換來的是要自己重新發明、自己扛責任的一套安全機制，對「保護所有網站密碼」這個定位來說不划算。願意接受商店審核流程帶來的不可控交付時間，以及之後每次擴充功能更新都要重新過一次審核的維護成本。

## 對版本管理的連帶影響

因為擴充功能更新要重新送審，密碼庫元件的版號**不跟 FileLocker 主體版號綁死**（發版節奏綁在一起、但版號各自獨立起算，見 `docs/specs/features/已完成/密碼庫_功能規劃.md`）——如果版號被迫跟著 FileLocker 主體同步，會出現「FileLocker 這次更新根本沒動到密碼庫，卻要為了湊版號重新送審」的情況，白白浪費審核等待時間。
