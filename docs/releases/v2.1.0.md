# FileLocker v2.1.0

## 繁體中文

`.flocked` 獨立加密升級為真正可攜（驗證材料嵌進檔案本身）、解密補上真實進度回報、加密前顯示磁碟空間預估，以及密碼庫改為消費獨立的 PasswordVault repo 部件並修正兩邊 App 共存時的瀏覽器整合連線問題。

### 亮點

- **`.flocked` 升級 v2，把驗證材料嵌進檔案本身**
  - 改版前 `.flocked` 檔案雖然自帶密文，但密碼驗證雜湊仍然只存在 Vault 的 `{uuid}.meta.json` 裡——檔案搬到別的裝置、或原本的 Vault 遺失、重建過，既存的 `.flocked` 全部打不開，跟「獨立可攜」的訴求不符。v2 把驗證材料放進檔尾，真正做到脫離 Vault 也能獨立驗證密碼與解密。
  - `.lockfolder` 標記檔同步補上驗證：改用比對防護索引（路徑必須確實在索引裡且狀態是 Locked），不再是讀出純文字內容就直接當資料夾路徑使用。
  - 改版前產生的 v1 `.flocked` 無法回溯補上驗證材料，仍只能靠 Vault 解密；重新以獨立加密模式加密一次即為 v2 格式。
- **加密流程收斂為單一路徑，修復巢狀資料夾防護重試失效**
  - 移除信封流程導入時保留的舊「一次到位」加密路徑（含依檔案大小估算的假進度條），一併發現並修復「加密內含防護中子資料夾時，解鎖後重試」的引導完全無法被觸發的問題。
  - 側欄「加密」改名為「檔案加密」，四個導覽項目統一為名詞。
- **保護等級重新分層，四套憑證各自命名**
  - 分層依據改為「後果有多不可逆」：永久刪除加密項目提升為最高等級（密碼 → 關鍵操作驗證 → 不可逆動作確認），清除使用紀錄（僅影響本機操作日誌）降為較低等級。
  - 資料夾防護的鎖定退避從「30 秒起跳、最長 1 小時」縮短為「5 秒起跳、最長 60 秒」——忘記防護密碼本來就可以透過檔案總管的安全性設定自行取回存取權。
  - 加密的密碼稱為「項目密碼」、資料夾防護的稱為「防護密碼」，密碼欄位旁固定顯示遺失後果，避免使用者混淆四套憑證各自忘記之後的實際影響。
- **解密補上真實進度回報**：GUI 還原中按鈕顯示「還原中... N%」；CLI 的 `encrypt`／`unlock`／`unlock-recovery` 由忙碌旋轉指示器改為真實百分比，數字來自實際處理掉的位元組數。
- **加密前顯示預估所需空間**：資料夾加密的峰值磁碟用量遠高於直覺（暫存 zip 與密文中途同時存在），事先提醒空間是否足夠，空間不足一律警示、足夠時僅在 1 GB 以上才給資訊性提示。
- **新增 CLI 獨立發布產物（CLI_setup／CLI_zip）**：只想要 CLI、不想裝完整 GUI 的使用者有更輕量的取得方式。
- **密碼庫改為消費獨立的 PasswordVault repo 編譯產出的部件**，並修正兩邊 App 共存時的瀏覽器整合問題：
  - `FileLocker.App` 的密碼庫下載來源、部件檔名，改指向 [PasswordVault](https://github.com/lx-kvn/PasswordVault) repo 的 Release。
  - 密碼庫資料改指向跟 `PasswordVault.exe` 共用的同一個實體資料夾，兩邊不再各自維護一份互相不同步的密碼庫。
  - 瀏覽器擴充功能的 Native Messaging Host 轉接程式改成兩邊共用同一份實體檔案，解決過去兩邊各自帶一份副本、登錄檔與 Named Pipe 兩套「贏家」判斷邏輯不一致時出現的「Pipe is broken」連線失敗。
- **修正一批這輪開發中發現的問題**：加密表單在視窗高度接近下限時內容超出畫面、按鈕按不到；CLI 輸入空密碼會讓整個行程帶著堆疊追蹤崩潰，而不是回報「密碼不正確」；密碼庫以外的介面文字（顯示用內文、按鈕上的字）雙擊會被意外選取。

### 已知限制

- **CLI 不涵蓋 Passkey**：設計決定，`KeyCredentialManager` 一定會跳出 Windows Hello 系統 UI，跟「無 GUI 環境可操作」的 CLI 存在目的直接衝突。
- **沒有數位簽章，也沒有執行檔完整性驗證機制**：安裝檔與更新下載回來的安裝檔執行時，Windows SmartScreen 可能會跳出警告。
- **軟體更新檢查僅支援透過正式安裝版比對版本**：直接以原始碼執行的開發版不會顯示版本資訊。
- **`.lockfolder` 標記檔在「依檔案類型分組」的檔案總管檢視下會被歸到跟資料夾不同的分組**：確認技術方向時已知情接受的取捨，換來的是不需要任何 COM／`IShellFolder` 程式碼、ACL 保護強度也不受影響。
- **改版前產生的 v1 `.flocked` 檔案無法回溯補上驗證材料**：仍然只能靠 Vault 解密，換裝置或 Vault 遺失後即無法開啟。
- **v2 `.flocked` 使檔案攜帶密碼驗證雜湊**：兌現「獨立可攜」承諾的必要條件，雜湊本身不可逆推回密碼，但檔案的可攜性使它比 `.meta.json` 更容易離開使用者的控制範圍。
- **背景模式（系統匣常駐）下，主視窗與系統匣選單的實際彈出位置不穩定**：不影響功能本身可以正常開啟與操作，僅彈出位置不理想，根因尚未完全確認。
- **PasswordVault 自己的 Native Messaging Host 登錄機制還沒實作**：只有 `FileLocker.App` 那一側會寫登錄檔／manifest，只裝 `PasswordVault.exe`、不裝 `FileLocker.App` 的使用者，瀏覽器擴充功能實際上連不上任何東西。
- **PasswordVault repo 的 Release 打包流程還沒能產出符合資產命名規則的 zip**：`FileLocker.App` 從 Release 自動下載、切換部件生效這條路徑，目前只驗證到程式碼層級，還沒有機會人工實測。
- 密碼遺失無法復原，沒有任何後門機制——請務必妥善保存密碼與恢復金鑰。

## English

`.flocked` standalone encryption is now truly portable (verification material embedded in the file itself), decryption gained real progress reporting, encryption now estimates required disk space up front, and Password Locker now consumes packages built from the separate PasswordVault repo, with a fix for the browser-extension connection issue when both apps run side by side.

### Highlights

- **`.flocked` upgraded to v2: verification material is now embedded in the file itself**
  - Before this release, a `.flocked` file carried the ciphertext but still relied on the Vault's `{uuid}.meta.json` for the password verification hash — move the file to another machine, or lose/rebuild the Vault, and every existing `.flocked` file became unreadable, defeating the "standalone and portable" promise. v2 stores the verification material in the file's trailer, so password verification and decryption now work fully independently of the Vault.
  - `.lockfolder` marker files got the same treatment: they're now validated against the Folder Guard index (the path must actually be present and in the `Locked` state), instead of being trusted as a plain-text folder path with no validation at all.
  - Pre-upgrade v1 `.flocked` files can't be retrofitted with verification material and still require the Vault to decrypt; re-encrypting them in standalone mode produces the v2 format.
- **Encryption consolidated into a single code path; fixed a broken nested-folder-guard retry**
  - Removed the legacy "all-at-once" encryption path (including its file-size-based fake progress bar) that had been kept around as a transition since the envelope flow was introduced. While removing it, discovered and fixed that the "unlock and retry" prompt for encrypting a folder containing a guarded subfolder could never actually be triggered.
  - The sidebar's "Encrypt" item is renamed to "File Encryption"; all four navigation items now use nouns consistently.
- **Protection tiers reordered by how irreversible the consequence is; each of the four credentials now has its own name**
  - Tiering is now based on "how irreversible the outcome is": permanently deleting an encrypted item is now the highest tier (password → critical-action verification → irreversible-action confirmation), while clearing usage history (which only affects a local log) was lowered to a lighter tier.
  - Folder Guard's lockout backoff was shortened from "starts at 30s, caps at 1 hour" to "starts at 5s, caps at 60s" — forgetting the guard password can already be recovered from via Explorer's own security settings.
  - The encryption password is now called the "item password" and the Folder Guard one the "guard password", with the consequence of losing each spelled out right next to the password field, so the four credentials' very different loss consequences aren't conflated.
- **Decryption gained real progress reporting**: the GUI's restore button now shows "Restoring... N%"; the CLI's `encrypt`/`unlock`/`unlock-recovery` switched from a busy spinner to a real percentage, driven by actual bytes processed.
- **Encryption now estimates required disk space up front**: encrypting a folder has a peak disk usage far higher than intuition suggests (a temporary zip and the ciphertext coexist mid-flight); the app now warns when space looks insufficient, and gives an informational hint only above 1 GB when space is sufficient.
- **New standalone CLI distribution (CLI_setup/CLI_zip)**: a lighter-weight way to get just the CLI without installing the full GUI.
- **Password Locker now consumes packages built from the separate PasswordVault repo, with a fix for the cross-app browser integration**:
  - `FileLocker.App`'s Password Locker download source and package file names now point at the [PasswordVault](https://github.com/lx-kvn/PasswordVault) repo's Releases.
  - Password Locker data now points at the same shared folder used by `PasswordVault.exe`, instead of each app maintaining its own out-of-sync copy.
  - The browser extension's Native Messaging Host relay is now a single shared binary used by both apps, fixing a "Pipe is broken" connection failure that occurred when each app carried its own copy and the registry (last-launched wins) and the named pipe (first-launched wins) disagreed on which copy was authoritative.
- **Fixed a batch of issues found during this round of development**: the encryption form's content overflowing and its buttons becoming unreachable near the minimum window height; the CLI crashing with a raw stack trace instead of reporting "incorrect password" when given an empty password; and UI text outside Password Locker being accidentally selected on a double-click.

### Known limitations

- **The CLI doesn't support passkeys**: a deliberate design decision — `KeyCredentialManager` always pops up the Windows Hello system UI, which directly conflicts with the CLI's reason for existing (usable in headless/no-GUI environments).
- **No code signing or executable integrity verification**: Windows SmartScreen may warn when running the installer or an update package you just downloaded.
- **The update check only works from an installed build**: running from source shows no version info.
- **`.lockfolder` marker files get grouped separately from their folder in Explorer's "group by type" view**: an accepted trade-off from when the technical direction was confirmed, in exchange for not needing any COM/`IShellFolder` code, with no impact on ACL protection strength.
- **Pre-upgrade v1 `.flocked` files can't be retrofitted with verification material**: they still require the Vault to decrypt and become unreadable if you switch devices or lose the Vault.
- **v2 `.flocked` files carry a password verification hash**: a necessary condition for the "standalone and portable" promise — the hash itself can't be reversed back into the password, but the file's portability makes it more likely to leave the user's control than `.meta.json` would.
- **In background mode, the main window and tray menu don't always pop up exactly where expected**: doesn't affect the app opening or working normally, only where it pops up; the root cause isn't fully confirmed yet.
- **PasswordVault's own Native Messaging Host registration isn't implemented yet**: only `FileLocker.App` writes the registry/manifest entry, so users who install only `PasswordVault.exe` (without `FileLocker.App`) currently can't connect the browser extension to anything.
- **PasswordVault repo's Release packaging pipeline can't yet produce a zip matching the asset naming convention**: the path where `FileLocker.App` auto-downloads and switches to a new package from a Release has only been verified at the code level, not manually tested end to end.
- A lost password cannot be recovered — there is no backdoor. Keep your password and recovery key safe.
