# FileLocker「單檔案分散式加密」功能規劃

**狀態：程式碼實作已完成（片 1-7 全部完成），待正式打包安裝程式後人工驗證雙擊 `.flocked` 解密的實際互動流程**（本文件是需求訪談定案紀錄，記錄討論過程與理由；實作階段發現規劃本身有問題的地方，已回頭修改本文件，見第 5、8 節與第 9 節「實作紀要」）

配套文件：[`CONTEXT.md`](../../../CONTEXT.md)（術語：集中庫加密、單檔案分散式加密、`.locked` 指標檔、`.flocked` 獨立密文檔）

---

## 1. 這是什麼

「單檔案分散式加密」是「加密」功能底下的第二種產出物存放模式，跟現有的**集中庫加密**（原本、唯一已實作的行為）並存，使用者在每一次加密操作時各自勾選要用哪一種，不是全域設定，也不影響先前已經用另一種模式加密過的項目。

兩種模式共用完全相同的密碼學保護（Argon2id 金鑰衍生＋AES-256-GCM）與密碼／Passkey／恢復金鑰三種解鎖方式，差別只在：加密後的內容放在哪裡、原始位置會不會留下東西。

| | 集中庫加密（現有） | 單檔案分散式加密（本文件） |
|---|---|---|
| 密文存放位置 | Vault 集中管理區 | 原地（或使用者另外指定的位置） |
| 原始位置留下什麼 | `.locked` 指標檔（僅含 UUID＋簽章，不含密文） | `.flocked` 檔案（本身就是完整密文） |
| 刪掉留在原位置的檔案，內容還在嗎 | 還在（Vault 裡的密文不受影響，清單頁顯示「已中斷連結」） | 不在（`.flocked` 檔案本身就是唯一副本，刪掉即遺失） |
| 清單頁能不能直接解密 | 永遠可以（密文在 Vault，跟指標檔現況無關） | 只要 `.flocked` 還在記錄的原始路徑上就可以；被移走的話不行，見第 6 節 |

這個風險落差是本功能設計上最需要留意的地方——「分散式」換來的是不依賴 Vault、內容留在使用者自己選的地方，但代價是**沒有集中備份**，`.flocked` 檔案本身遺失即等於資料遺失，不像集中庫加密那樣有 Vault 這一層保底。

## 2. 範圍

跟現有加密功能同範圍：單一檔案、多選批次、資料夾都支援。「單檔案」指的是**產出物的形狀**——不論輸入是一個檔案還是一整個資料夾，加密後永遠是原地的單一顆 `.flocked` 檔案（資料夾一樣先壓縮成一份再加密，封裝方式跟集中庫模式相同，只有落腳位置跟副檔名不同），不是限制輸入只能是單一檔案。

## 3. UI 入口

信封加密流程（`EnvelopeEncrypt.vue`）新增一個勾選項，預設不勾（預設走集中庫加密，維持現有行為不變）。勾選後：

- 額外出現一個「存放到其他地方」的次要勾選項，不勾的話預設原地取代原始檔案。
- 勾選「存放到其他地方」則跳出資料夾選擇對話框，讓使用者指定 `.flocked` 檔案要放去哪裡（跟資料夾防護的既有模式不同，這裡選的是目的地資料夾，不是原地）。

UI 文案（勾選框上顯示給使用者看的字）留待實作階段另外討論用詞，不強制跟內部詞彙「單檔案分散式加密」逐字對應。**定案**：勾選框顯示簡短的「獨立加密」（英文 "Standalone encryption"），完整說明（「加密結果不會存進集中管理區…」）改放進 hover 才會出現的提示泡泡（沿用既有 Passkey／恢復金鑰旁邊那顆 `?` 提示框的樣式）——內部程式碼命名（`StorageMode.Standalone`、`enableStandaloneMode` 等）維持不變，只有這個 UI 顯示字跟原本的內部詞彙不再逐字對應，理由是「單檔案分散式加密（不存進集中管理區）」塞進勾選框太長，容易把整排選項擠爆版面。

## 4. 副檔名：`.flocked`

現有 `.locked` 指標檔只是一個指標——內容只有 UUID＋HMAC-SHA256 簽章（見 `LockedMarkerFile`），真正的密文另外存在 Vault 的 `{uuid}.enc`。單檔案分散式加密沒有 Vault 可以指過去，`.flocked` 檔案本身就必須背著完整密文，檔案大小跟原始內容同等級，跟現有指標檔那種幾百 bytes 的小檔案是完全不同性質的東西。

副檔名刻意跟 `.locked` 同一家族但取不同名稱（`.flocked`，在 `.locked` 前面加一個 `f`，代表 "FileLocker standalone"），原因：

1. 雙擊時 App 要能單靠副檔名就判斷「這是指標檔（去 Vault 撈密文）」還是「這是獨立密文檔（直接原地解密自己）」，不需要先解析檔案內容才知道類型。
2. `FolderArchiver` 掃描巢狀鎖定項目（`FindNestedLockedFiles`，現在只掃 `*.locked`）需要同時認得 `.flocked`，才能正確攔下「資料夾裡混了分散式加密檔案」這種巢狀情境，不能讓 `.flocked` 檔案被外層資料夾的集中庫加密整批吞掉而不自知——這是實作階段要記得同步更新的既有函式。

## 5. Icon

跟現有指標檔用同一個視覺家族（都是文件＋鎖頭意象、同色系，一眼看得出是 FileLocker 的東西），但加兩條代表文字內容的線做區分：

- `.locked` 指標檔：文件＋鎖頭，無內容線——視覺上暗示「這只是個指標，沒有東西」。
- `.flocked` 獨立密文檔：文件＋鎖頭＋兩條內容線——視覺上暗示「裡面真的裝著東西」。

理由見第 1 節的風險落差：`.flocked` 檔案本身遺失即資料遺失，比 `.locked` 指標檔遺失（內容仍在 Vault）嚴重得多，icon 需要讓使用者一眼看出「這顆比較重要，別亂刪」，不能跟指標檔共用同一顆讓使用者誤以為兩者風險相同。

實際 SVG／ICO 稿已完成，兩種用途各自獨立：`assets/Locked_File_flocked_icon.svg` 是信封加密 UI 勾選框旁邊的小圖示（單一尺寸，直接內嵌前端）；`assets/Locked_File_flocked.svg`／`.png`／`.ico`（多尺寸，16~256px）是 Windows 檔案總管的 `.flocked` 副檔名圖示。

Windows Explorer 檔案類型圖示的**註冊機制定案為「跟 `.locked` 走同一套」**——不是本節原本寫的「比照 `ShellExtensionRegistrar` 現有 `.lockfolder` 圖示註冊模式」。理由：`ShellExtensionRegistrar`／`.lockfolder` 那套是 App 啟動時自我註冊、寫入 HKCU 的機制，服務對象是「資料夾標記檔」；`.locked`／`.flocked` 都是「單一檔案雙擊直接解密」，本質上是同一類東西，改用安裝程式當下（`installer_config.json` 的 `file_associations`／`doc_icons`）靜態註冊的既有模式，不需要另外寫一套自我註冊邏輯。詳見第 8 節、第 11 節。

## 6. Metadata 與清單頁

### 6.1 `StorageMode` 欄位

`LockedItemMetadata` 新增欄位 `StorageMode`，型別為新增的 enum：

```csharp
public enum StorageMode
{
    Vault,       // 集中庫加密（預設值，沿用舊資料——沒有這個欄位的舊版 .meta.json 反序列化時自動補上，不需要額外遷移邏輯，比照既有 Status 欄位的處理方式）
    Standalone   // 單檔案分散式加密
}
```

`StorageMode` 決定「密文放哪裡」，跟既有 `Status`（`Pending`／`Committed`，決定「這筆加密有沒有真正完成」）是兩個互相獨立的軸，交叉會出現四種組合，第 7 節另外討論 `Standalone`＋`Pending` 這個組合要注意的地方。

### 6.2 Vault 裡仍然寫一份純書籤 metadata

`StorageMode=Standalone` 的項目，Vault 裡照樣寫一份 `{uuid}.meta.json`（記錄原始路徑、密碼驗證雜湊等——這些本來就不是機密，跟集中庫加密的 metadata 性質相同），**唯獨不寫對應的 `{uuid}.enc` 密文檔**（密文已經在 `.flocked` 檔案本體裡了）。

這個決定讓清單頁跟移動/刪除偵測完全複用現有機制，不需要另外設計一套平行的索引系統：

- **清單頁顯示**：`VaultIndexCache` 照樣把這筆 metadata 收進索引（前提是它的 `Status` 是 `Committed`——沿用最近才修好的「`Pending` 項目不該出現在清單」規則，見 `VaultIndexCache.cs` 的 Schema 2 filter），清單頁不需要為了 `StorageMode` 另外分支處理「怎麼顯示」。
- **移動/刪除偵測**：複用 `MarkerStatusChecker` 的邏輯，只是檢查目標從 `.locked` 換成 `.flocked`——`StorageMode=Standalone` 的項目改成檢查 `{OriginalName}.flocked` 存不存在於 `OriginalPath` 記錄的位置，找不到就顯示「已變更位置或已刪除」（比照使用者這次提出的需求原句）。

## 7. Pending/Commit 交易模型的延伸

現有集中庫加密的「取消要能安全回滾」交易模型（`EncryptPendingAsync`／`CommitEncryptAsync`／`RollbackPendingEncryptAsync`，信封 UI 使用者確認前可以隨時安全放棄）需要延伸到 `Standalone` 模式，但「commit」這一步實際做的事不同：

- 集中庫加密 commit：寫 `.locked` 指標檔、刪除原始檔案、`Status` 改 `Committed`。
- 單檔案分散式加密 commit：把暫存的加密輸出**移動/覆蓋到最終位置**（原地或使用者指定的另一個資料夾）、刪除原始明文、`Status` 改 `Committed`。

`Standalone`＋`Pending` 這個中間態要確保：使用者按取消時，原始檔案完全沒被動過，暫存的加密輸出（不管放在系統暫存目錄還是別的地方）要能被安全清掉，跟集中庫模式「pending 階段原始檔案全程沒被動過」的既有保證一致。這部分的暫存檔案放置位置與清理細節留待實作階段設計。

## 8. 解密入口

- **清單頁項目正常存在（`.flocked` 還在記錄的原始路徑上）**：跟集中庫加密一樣，可以直接從清單頁觸發解密（密碼／Passkey／恢復金鑰皆可），差別只在解密時讀密文的來源從 Vault 的 `{uuid}.enc` 換成直接讀 `.flocked` 檔案本體。
- **`.flocked` 檔案被移走**：清單頁該項目顯示「已變更位置或已刪除」，**不提供從清單頁直接解密的入口**——因為 App 不知道檔案現在在哪，硬要提供入口只會導致「點了沒反應」或「你自己選一個檔案讓我猜對不對」這種更差的體驗。
  - 解密方式退回現有的「雙擊 `.locked` 檔案解密」同一套入口：使用者自己找到 `.flocked` 檔案本體、雙擊它，App 判斷副檔名後直接讀取檔案本身內含的密文解密。
  - 清單頁該項目提供一顆「前往檔案原始位置」按鈕，複用現有 `openFolderInExplorer` IPC（`MainWindow.xaml.cs` 的 `HandleOpenFolderInExplorer`，加密流程其他地方已經在用），開啟原始路徑所在的資料夾，方便使用者就近尋找（例如檔案只是被移到同一層樓的另一個資料夾）。**不做**「手動重新關聯到新路徑」這種讓使用者手動修正 metadata 的介面——這是可以之後再視需求加上的錦上添花功能，不在這輪範圍內，先確保雙擊本體一定能解密即可，不依賴清單頁記不記得路徑。

**修正（實作階段發現本節原文有誤）**：上面「不需要查 Vault」這句原本的描述不精確——雙擊 `.flocked` 解密**仍然需要查 Vault**，因為密碼驗證用的鹽值、Argon2 參數等 metadata（見第 6.2 節）並沒有跟著搬進 `.flocked` 檔案本體，commit 時只有密文本體被搬走，`{uuid}.meta.json` 原地留在 Vault。真正不需要查 Vault 的只有「密文內容」這一項——這正是 `.flocked` 跟 `.locked` 唯一的實質差異，其餘（密碼驗證、Passkey、恢復金鑰）兩種模式共用完全相同的邏輯。

另外，雙擊入口刻意**不透過 metadata.OriginalPath 反推 `.flocked` 位置**，而是直接使用者實際點開的那個檔案路徑讀取密文、以它所在資料夾為還原目的地——這是為了讓「獨立可攜」（第 1 節）這個賣點站得住腳：使用者把 `.flocked` 搬到跟加密當下完全無關的資料夾之後，雙擊還是要能正常解密，不能因為 `metadata.OriginalPath` 記錄的舊位置對不上就失敗。這跟清單頁的「已變更位置或已刪除」判斷（依賴 `OriginalPath`）是兩條獨立的路徑，互不影響：清單頁的判斷只是「要不要顯示直接解密的按鈕」這個 UI 提示，雙擊本體解密永遠以使用者手上這個檔案的實際位置為準。

## 9. 實作紀要（片 1-7 完成後補記）

實作依 `LockedItemMetadata`／`VaultIndexCache`（片1）→ `.flocked` 格式＋狀態檢查（片2）→ 巢狀鎖定偵測（片3）→ Pending/Commit/Rollback 交易模型延伸（片4）→ IPC＋前端 UI（片5）→ CLI（片6）→ 檔案總管雙擊解密＋安裝程式（片7）的順序完成，每片先寫測試、確認符合規劃行為之後才動手實作。跟本文件規劃有出入、值得記錄的調整：

- **`.flocked` header 加了長度欄位＋保留位元組**：原規劃只講「加一段非加密的小 header（magic bytes＋版本＋UUID）」，沒講固定長度會擋住未來擴充。實作時發現這個問題，改成 Magic(4)+版本(1)+Header 長度(2)+UUID(16)+保留(8) = 31 bytes，讀取端永遠照宣告的長度跳過，不是寫死常數——之後要在保留欄位塞真正用得到的東西不用跳版本號。這個教訓後來被記錄成 `CLAUDE.md` 的專案層級開發原則（「對未來程式發展保留擴充空間」一節，直接引用這個案例）。
- **Standalone 模式的 Pending 階段暫存位置，沿用 Vault 既有的 `{uuid}.enc` 暫存位置**，不是第 7 節原本設想的「系統暫存目錄」——`EncryptToVault` 寫入時如果是 Standalone 模式，先把 `.flocked` header 寫進同一個 Vault 暫存串流，密文緊接在後面，這樣 Pending 階段這個檔案本身就已經是一份合法的 `.flocked` 內容，只是暫時放在 Vault 資料夾、副檔名還是 `.enc`。好處：Rollback 完全不用改，`_vault.DeleteItem(uuid)` 原本就會刪掉這個暫存檔，不需要另外設計一套系統暫存目錄的清理邏輯。
- **`LockedItemMetadata` 新增 `StandaloneDestinationDir` 欄位**：commit 只吃 `uuid`，沒辦法從呼叫端另外拿到使用者選的目的地資料夾，只能存進 metadata 裡跨 Pending/Commit 兩個階段傳遞；commit 完成後 `OriginalPath` 會更新成 `.flocked` 實際落腳的位置。
- **Explorer 檔案類型圖示註冊機制**：見第 5、8 節，定案改成比照 `.locked` 由安裝程式 `installer_config.json` 靜態註冊（`file_associations` 陣列＋`doc_icons` 字典），不是原規劃寫的比照 `ShellExtensionRegistrar`。這個決定額外受惠於 mac-style-windows-installer 專案在規劃期間已經完成的 `doc_icons`（v0.10.0，讓不同副檔名各自套用不同 ICO）功能，不需要為了這個需求再去改那個獨立專案的程式碼，只需要更新這個 repo 的 `installer/filelocker_installer.json` 設定。
- **雙擊 `.flocked` 解密不透過 metadata.OriginalPath 反推位置**：見第 8 節的修正說明，直接用使用者實際點開的檔案路徑讀取密文＋決定還原目的地，支援「檔案被搬到別的資料夾後還能雙擊解密」。

片 7 完成後實測（使用者實際加密＋操作 App 時發現，非規劃階段預見），額外修了 3 個回歸：

- **清單頁誤判「指標檔可能被移動或刪除」**：`VaultProtocolHandlers.ListVaultAsync` 原本無論 `StorageMode` 是什麼都固定呼叫 `MarkerStatusChecker` 查 `.locked` 在不在，Standalone 項目本來就不會有 `.locked`，剛加密完馬上就被誤判成「找不到」。改成依 `entry.StorageMode` 分派給 `MarkerStatusChecker` 或 `FlockedStatusChecker`，連帶把「被別的項目取代」「被收進資料夾一起加密」兩種訊息文案也修成正確用詞（新增 `ErrorCodes.FlockedReplacedByOtherNamed`／`FlockedPackedIntoContainer`）。**這個修正順帶把第 11.1 節原本列的「清單頁『已變更位置或已刪除』狀態顯示」待辦也一併做完了**——`FlockedStatusChecker`（片2）本來就有偵測邏輯，缺的只是這裡的接線，不是另外要做的新功能。
- **「解密」頁籤手動選檔案完全不認得 `.flocked`**：原生選檔視窗的副檔名篩選、`InspectLockedFile`（讀取顯示用 metadata）、`DecryptAsync`（送出密碼解密）三個地方都只認 `.locked`，選 `.flocked` 送出去一律判定「找不到或無法解析」，即使密碼完全正確。三處都補上依副檔名分派的邏輯，跟雙擊入口共用同一套判斷方式。
- **解密信封彈出後密碼輸入框沒有自動拿到鍵盤焦點**：使用者體驗回饋，跟前兩個不算同一類「判定漏掉 `.flocked`」的 bug，但同一輪一起處理。`EnvelopeDecrypt.vue` 新增 `focusActiveInput()`，sheet 落定的瞬間、Passkey 驗證失敗退回表單、切換密碼／恢復金鑰分頁時都會自動搶焦點，比照 `PasswordPromptWindow.xaml.cs`（雙擊檔案跳出的原生小視窗）既有的 `PasswordInput.Focus()` 行為。

## 10. 已知限制（規劃階段即可預見，非缺陷）

- **沒有集中備份**：`.flocked` 檔案本身就是唯一副本，遺失即資料遺失，這是「分散式」這個設計本身的必然取捨，不是可以修正的缺陷，需要在 UI 上以某種形式提醒使用者（例如勾選這個選項時跳出一次性提示），實作階段另外設計提示文案與時機——**這輪 7 片實作沒有涵蓋這個提示**，仍然是待辦（見第 11 節）。
- **不支援手動重新關聯路徑**：見第 8 節，`.flocked` 被移走後只能靠使用者自己找到本體雙擊解密，清單頁不提供「選一個新路徑」的修正介面。
